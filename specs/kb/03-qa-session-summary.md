# Q&A-сессия с заказчиком (16.09.2026) — выводы

Полный конспект: [source/qa_session_2026-09-16.txt](source/qa_session_2026-09-16.txt). Здесь — что уточнили и что это меняет в решении.

## Главное изменение: кто обучаемый

**Не оператор 112, а диспетчер ДДС.** Диалог «заявитель звонит в 112» из MVP **исключён полностью**: записи заявителей не нужны, ИИ-заявитель с ветвлением не нужен. Генерация голоса заявителя — бонус «на перспективу», жюри оценит как плюс, но не требует.

### Реальный процесс, который симулируем

1. Карточка (уже заполненная оператором 112 или пришедшая из внешней системы) **падает в очередь** диспетчера ДДС.
2. Диспетчер обязан открыть её и проставить первичный статус **за 30 секунд**.
3. Читает фабулу, адрес, признаки → принимает регламентное решение: принять / не принять / направить бригаду / связаться со смежниками. Заполняет поля вручную.
4. **Звонит по софтфону руководителю службы** (внутренний 3–4-значный номер), проговаривает вводную. ИИ отвечает: «Слушаю» → «Понял, информация принята». Желательна вариативность голосов (муж/жен, интонация по службе).
5. Проводит карточку по **полному жизненному циклу**: Принята → Начало реагирования → Прибытие → Проведение работ → Работы завершены. Полная отработка — **3 минуты**.
6. Пока работает — в очередь падают **новые карточки**. Многозадачность обязательна, намеренно провоцирует ошибки ручного ввода.

Точки A/B/C из ответа заказчика: A — заявитель (исключён), B — диспетчер ДДС (обучаемый), C — руководитель смены / начальник бригады (ИИ-ответчик).

## Остальные уточнения

| Опросные карты | Единого документа нет (система модернизируется). Дадут типовой сценарий (ДТП с разливом топлива и пострадавшими). |
| Методика оценки | **Официальной нет — веса и шкала на усмотрение команды.** Обязательные критерии: время по этапам, корректность полей, грамматика/орфография ручного ввода. Сравнение **смысловое, не побуквенное**. |

## Вопросы, оставшиеся без ответа

- Допустимы ли готовые инструменты без собственной архитектуры нейросетей; что приоритетнее — концепция или глубина реализации.
- Какие нефункциональные требования (TLS, отказоустойчивость, 100 пользователей, бэкапы) обязательны для прототипа.
- Можно ли ограничиться несколькими ключевыми ДДС; какие помехи (шум, эмоции, перебивания) учитывать в первую очередь.

## Что это меняет для команды

- **ИИ-инженер:** вместо диалогового ИИ-заявителя — генерация вариаций сценариев из билетов + простой голосовой ответчик «слушаю / принято» (STT → короткая логика → TTS).
- **Фронт:** очередь карточек, карточка с полным жизненным циклом статусов, софтфон, экран преподавателя с мониторингом класса.
- **ML:** движок оценки становится центральным — оценивается последовательность действий по жизненному циклу, корректность полей, адреса/опечатки, голосовой доклад, тайминги по этапам, многозадачность; адаптивная сложность; калибровка по правкам преподавателя. См. [05-ml-plan.md](05-ml-plan.md).
- **Отпало:** разбор длинного транскрипта с заявителем, классификатор намерений диспетчера в реальном времени, акустика голоса.
