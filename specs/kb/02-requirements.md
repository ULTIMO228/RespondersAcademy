# Требования (структурированное ТЗ)

Источник: [source/tz_full_extracted.txt](source/tz_full_extracted.txt). Здесь — выжимка с пометками, что обязательно, что опционально, и что скорректировано Q&A-сессией (см. [03-qa-session-summary.md](03-qa-session-summary.md)).

## 1. Продукт

Веб-сервис, работающий **в изолированной локальной сети учебного центра без интернета**.

- Браузеры: Chrome, Firefox, Яндекс.Браузер. ОС: Windows 10/11, Ubuntu 20.04+.
- СУБД: PostgreSQL 12+.
- Имитирует АРМ-112 для диспетчеров ДДС городского хозяйства (Гормост, ЖКХ, Мосводоканал, Москоллектор, газ и др.).
- **Не** обрабатывает реальные вызовы, **не** содержит функций настоящей Системы-112 — только имитация.

## 2. Обязательные модули (раздел «Требования к сервису»)

1. **Эмулятор АРМ-112** — интерфейс и рабочий процесс оператора в реальном времени, аутентичный полям реальной карточки (номер, телефоны заявителя, адрес, статусная строка, фабула, список оповещения).
2. **Имитация входящих вызовов** — через виртуальную IP-телефонию (софтфон/WebRTC) **или** текстовые сообщения. Аппаратный IP-телефон и реальные SIP-вызовы не требуются.
3. **Инструменты преподавателя** — управление обучением.
4. **Оценка действий на основе нейросетевого анализа** — включая анализ ручного ввода текста.
5. **Уровни сложности заданий.**
6. **Изолированный контур** — без внешних сетей.

Сквозные обязательные: аутентификация (логин/пароль достаточно), RBAC на три роли, TLS внутри контура, аудит действий, бэкап раз в сутки, отчётность.

## 3. Роли

### Администратор
Учётные записи, роли, блокировка; запуск/остановка сервисов; мониторинг и логи; бэкапы; настройки VoIP/БД/безопасности. **Не может** менять оценки и сценарии во время занятия.

### Преподаватель
- Создаёт, редактирует, **утверждает сценарии, в том числе сгенерированные нейросетью**.
- Задаёт параметры генерации: тип происшествия, локация, сложность.
- Назначает задания ученикам и группам; настраивает фильтр «ученику ЖКХ — только события ЖКХ».
- Ставит нормативы времени и критерии успешности (порог ошибок, требования к синтаксису).
- Мониторит занятие в реальном времени (экраны всех курсантов в локальной сети), завершает его в любой момент.
- Видит результаты: **авто-оценка ИИ + своя экспертная оценка**, комментирует. Изменение оценки — только с записью в журнал аудита.
- Получает отчёты и **ИИ-инсайты по типичным ошибкам группы**.

### Обучающийся
Видит назначенные сценарии и справочные материалы; принимает карточки/вызовы; заполняет карточку; видит таймер, свои оценки, время реакции, историю ошибок и рекомендации. Чужие результаты не видит.

## 4. Пользовательские сценарии (= демо-путь)

### A. Настройка учебной среды (преподаватель)
Выбор категории событий → нейросеть генерирует сценарии → система формирует **эталонные ответы** → преподаватель видит предпросмотр с подсветкой правильных ответов → утверждает полностью/частично → при ошибке пишет комментарий в контекстное поле, система **перегенерирует с учётом комментария** → опционально загружает свои материалы → принудительная проверка грамматики после ручных правок.

### B. Занятие «Карточки»
Преподаватель выбирает категории (можно несколько) → старт → система имитирует поступление карточки/звонка → ученик отрабатывает карточку → преподаватель завершает → отчёт.

### C. Занятие «Действия с карточками»
Система выдаёт готовую карточку (сгенерированную / созданную учениками / смешанно) → ученик вводит текстовое действие («Сообщение принято, бригада направлена») → следующая карточка → … → отчёт.

**Отчёт (для B и C):** действия, ошибки, время заполнения, отклонение от норматива, грамматика.

## 5. Что должен делать ИИ/ML

| Функция | Откуда в ТЗ |
|---|---|
| Генерация сценариев по типу/локации/сложности | сценарий A |
| Автоформирование эталонных ответов | сценарий A |
| Перегенерация по комментарию преподавателя | сценарий A |
| Имитация абонента (голос или текст) | сценарий B, требование 2 |
| Сравнение ручного ввода с эталоном (по смыслу) | постановка задачи |
| Контроль тайминга и регламента | везде |
| Проверка грамматики/орфографии | сценарии A, B, C (4 упоминания) |
| Инсайты по типичным ошибкам группы | роль преподавателя |
| Рекомендации ученику | роль обучающегося |
| Адаптивная сложность («прогнозирование») | критерии экспертизы + Q&A |

Всё — на локальных моделях, **только CPU, типовые офисные ПК** (по Q&A; в ТЗ был сервер i7/Xeon, 32 ГБ RAM, NVMe).

## 6. Опциональные (раздел 6 ТЗ)

Расширенная аналитика с графиками и тепловыми картами ошибок; экспорт в Excel/PDF; пакетный импорт сценариев; мобильный интерфейс; внутренний API.

## 7. Производительность (заявлено, на хакатоне не проверяемо)

100 пользователей / отклик ≤2 с; 20 одновременных сессий; VoIP ≤150 мс; переживание обрыва сети до 30 с; 100 записей/с в БД; отчёт ≤30 с; вертикальное и горизонтальное масштабирование.

## 8. Форматы данных

JSON — сценарии, обмен, логи, профили. XML — конфиги. CSV — отчёты. SQL — БД. MP3/WAV — записи вызовов. PDF — сертификаты, документы. DOCX — методички.

## 9. Критерии экспертизы

**Предварительная:** идея и оригинальность; качество кода, интегрируемость, скорость; «проверка расчётов и достоверность прогнозирования»; полнота документации.

**Финальная:** то же + реализация настраиваемых параметров; объективность и наглядность диаграмм; UX/UI (десктоп + мобильный, логически связанные блоки рядом); «рекомендации сервиса соответствуют реальным»; питч.

Часть формулировок («прогнозы соответствуют поведению инфраструктуры») скопирована из другого кейса. Для нас «прогнозирование» = адаптивная сложность (подтверждено на Q&A), «достоверность» = совпадение авто-оценки с экспертной.

## 10. Что реально за 2 недели

**Ядро:** роли + вход; преподаватель генерирует и утверждает сценарии; очередь карточек у ученика; полный жизненный цикл карточки; режим «действия с карточками»; авто-оценка (эталон + тайминг + грамматика); отчёт по занятию; мониторинг в реальном времени.

**Сильно желательно:** софтфон «диспетчер → руководитель службы» с ИИ-ответчиком (Vosk + Silero); аналитика с тепловой картой; экспорт CSV/PDF; валидация оценщика на размеченной выборке; адаптивная сложность.

**Показать архитектурно, не реализовывать полностью:** SIP-сервер, бэкапы по расписанию, TLS, горизонтальное масштабирование, восстановление сессий при обрыве.
