## R15. Совместимость контракта: тот же URL-префикс, rewrite в Next.js

- **Decision**: FastAPI монтирует совместимый роутер под `/api/mock` и зеркально под `/api/v1`. Фронт подключается через `rewrites()` в `next.config.ts` (`beforeFiles`: `/api/mock/:path*` → `${BACKEND_URL}/api/mock/:path*`, только если задан `BACKEND_URL`). Без переменной фронт работает на своём мок-слое, как сейчас.
- **Rationale**: FR-059 — фронт не меняется; `beforeFiles` перекрывает route-handler'ы `app/api/mock/**`; запросы остаются same-origin, cookie `arm112_session` уходит без CORS/credentials; `scripts/e2e-*.sh` работают без правок (они ходят через `BASE_URL/api/mock`). В проде nginx делает то же самое.
- **Alternatives**: `NEXT_PUBLIC_MOCK_API_BASE_URL=http://host:8000/api/mock` + CORS — клиент `fetch` не шлёт cookie кросс-ориджин (`credentials` по умолчанию `same-origin`), пришлось бы править `client.ts`; удалять route-handler'ы фронта — ломает Vitest фронта.

## R16. Сессия: cookie фронта + подписанный токен

- **Decision**: `POST /auth/login` возвращает `AuthSession { userId, role, token, twoFactorUsed, issuedAt }`, где `token` — JWT HS256 (`sub=userId`, `role`, `iat`, `exp = iat + 24 ч`). Фронт сам кладёт JSON в cookie `arm112_session` (URL-encoded). Бэкенд в `deps.get_viewer()` читает cookie → JSON → проверяет подпись и срок `token`; также принимает `Authorization: Bearer <token>` (для тестов и будущих клиентов). Пароли — argon2-хэши, сиды хэшируются при загрузке; `reset-password` генерирует временный пароль и возвращает его один раз, как в моке. 2FA: `twoFactorCode` принимается и не проверяется (заглушка, как во фронте; `AuthPolicy.twoFactorRequired` из настроек).
- **Rationale**: FR-062; фронт уже разбирает cookie в `proxy.ts` и серверных лэйаутах по своим правилам (24 ч от `issuedAt`) — бэкенд не должен менять формат. Мок-эндпоинты cookie не проверяют, а бэкенд обязан (изоляция T2.5-01) — поведение для анонима повторяет мок: без cookie запросы с `sessionId` работают, с `studentId` → 401.
- **Alternatives**: HttpOnly-cookie, выставляемая бэкендом, — фронт её не прочитает для `sessionStore`; сессии в БД — лишняя таблица для 20 пользователей.

## R17. Оценщик → `Evaluation` фронта

- **Decision**: `ml.assess.engine.assess(attempt, scenario, cards, config) -> AssessmentResult` (компоненты, ошибки с правилами, предупреждения) и адаптер `to_evaluation()`: `timeScore` = компонент `timing`; `correctnessScore` = среднее взвешенное `decision + statuses + fields + multitask`; `grammarScore` = `grammar + address`; `semanticScore` = `comments (+ report)`; `totalScore` = Σ weight·score × 100 (веса — `Scenario.successCriteria`/план занятия, по умолчанию из R14-001: время 0,25; решение 0,2; статусы 0,15; комментарии 0,15; поля 0,1; грамотность 0,1; многозадачность 0,05); `errors[] = { type, severity, message }`, где `message` = «<текст> — <правило-источник>»; `grammarErrors[]` из R2/R3; `aiComment` — детерминированный текст из шаблонов по компонентам (без LLM), начинается с «ИИ-оценка:». Полный `AssessmentResult` (компоненты, веса, `ruleId`, `step`, `fixed`) хранится в `evaluations.components` для разбора и калибровки.
- **Rationale**: контракт `Evaluation` фиксирован фронтом; принципы II/III требуют сохранить детализацию — храним обе формы. Эталон волны A — `Scenario.etalon` (`expectedActions`, `keyPhrases`, `expectedFields`, `expectedText`) + `IncidentCard.expectedServices/expectedTags` + `timeNorms`.
- **Alternatives**: расширять `Evaluation` новыми полями — допустимо (фронт игнорирует лишние), но менять существующие нельзя.

## R18. Хранилище: PostgreSQL целевая, SQLite для разработки

- **Decision**: SQLAlchemy 2 async; `DATABASE_URL` по умолчанию `sqlite+aiosqlite:///backend/var/dev.db`; в проде `postgresql+asyncpg://…`. Вложенные структуры фронта (`notificationList`, `cardFlow`, `statuses[]`, `charts`, `etalon`, `settings`) — `JSON().with_variant(JSONB, "postgresql")`. Alembic-миграции генерируются под PostgreSQL; для SQLite используется `metadata.create_all` (тесты).
- **Rationale**: на машине разработчика нет PostgreSQL и Docker; тесты должны бежать без внешних сервисов; конституция требует PostgreSQL 12+ для поставки — обеспечено. Запросов, требующих JSONB-операторов, в контракте нет (фильтры карточек делаются по колонкам + в памяти на 108 карточках).
- **Alternatives**: только PostgreSQL — блокирует разработку сегодня; `testcontainers` — нужен Docker.

## R19. Сиды и семантика ID

- **Decision**: `backend/app/seed/load.py` читает `spec/mocks/*.json`, `spec/mocks/fixtures/arm-cards.json`, `mocks/local/addresses.json`, `mocks/admin/*.json` (пути относительно корня репо, переопределяются `SEED_DIR`); загрузка идемпотентна (upsert по `id`); `meta.*` игнорируется; `reference.classifierRows.$ref` разрешается в таблицу классификатора; `X-Classifier-Version` = `classifier.meta.version`. Новые записи получают ID в тех же форматах: `u-NNN`, `s-NNN`, `ses-NNN`, `att-NN`, `mat-NNN`, `rep-<хвост sessionId>-<studentId>`, `rep-…-group` (счётчики — по максимальному существующему номеру). Отчёты `reports.json` помечаются `static=true` и никогда не пересобираются.
- **Rationale**: FR-060 и тесты фронта (`scripts/e2e-*.sh` ссылаются на `ivanov/student112`, `c-063`, `ses-2026-09-16-01`, `att-01`); `sessions.json` уже содержит миграцию ID (см. `meta.note`).
- **Alternatives**: UUID + маппинг — ломает e2e и демо-подсказки на `/login`.

## R20. Репликация рантайм-семантики мок-слоя

- **Decision**: перенести 1:1 доменную логику фронта (TypeScript → Python) для: (a) машины статусов ДДС из `reference.ddsStatuses[].next` (`invalidTransition` 409, `requiresComment` 400); (b) `cardFlow` при старте занятия по `SessionPlan` (темп, порядок, конвейер, категории, профили; без плана — шаг 3 мин); (c) окна ленты `(since, at]` с порядком «выдача → открытие → статус → завершение → оценка ИИ, затем курсант, карточка»; (d) `control` (pause/resume/issue/report) и переход `finished → reported` с формированием отчёта; (e) ленивой сборки отчёта при `GET /reports` для завершённого занятия, идемпотентно; (f) проекции `GET /cards` для `c-NNN` поверх фикстуры по `fixture-map`; (g) расширенного поиска карточек (AND между полями, OR внутри, ё/е и регистр не различаются). Источник истины — `src/entities/*/model/**`, `src/shared/api/mock/**`; каждый пункт покрывается unit-тестом с теми же примерами, что в `*.test.ts` фронта.
- **Rationale**: FR-059: e2e-скрипты и экраны зависят от этих деталей; проще перенести, чем переизобретать.
- **Alternatives**: считать «достаточно похожее» поведение — риск расхождений на защите.

## R21. Генерация сценариев без LLM и с LLM

- **Decision**: `POST /scenarios/generate` синхронно, как в моке (≤ 3 сценария): при доступном Ollama (`OLLAMA_URL`, health-check при старте) — LLM с JSON-схемой и повторами; иначе — детерминированный шаблонный генератор (вариации по группе: комбинирует карточки `cards.json` той же группы, меняет адрес из `mocks/local/addresses.json`/справочника улиц, ловушки по параметрам). Оба пути проходят валидатор R22 и помечаются `source: generated`, `validation.status: pending`. Повторный вызов с той же категорией не дублирует (по `title`), как в моке.
- **Rationale**: демо не должно зависеть от наличия 4,7 ГБ модели; принцип IV. LLM-путь остаётся для SC-008.
- **Alternatives**: фоновая задача с `job_id` (как в 001) — контракт фронта синхронный; оставить асинхронность для `/api/v1` волны B.

## R22. Валидатор билетов, справочник ситуаций и рекомендательная система

- **Decision**: **Валидатор** (FR-023) — `ml.generate.validator.validate(ticket) -> ValidationReport { checks: [{ id, passed, confidence?, message }] }`: категория (R4, порог уверенности 0,6 → «требует ручной проверки»), адрес (R3), обязательные поля, дубликат (косинус e5 ≥ 0,92 к существующим), грамматика (R2), согласованность фактов (правила: «пострадавшие» в тексте ↔ `victims`, «03 не требуется» ↔ `noAmbulance`, регион ↔ `crossRegion`). **Справочник** (FR-046) — статьи генерируются скриптом из классификатора и памятки в `backend/data/kb/*.md` (по группе ЕКП: признаки, службы, что уточнить, ожидаемое решение ДДС, типичные ошибки) и загружаются как сид; правки преподавателя — в БД. **Рекомендации** (FR-047) — детерминированная модель: профиль ошибок обучаемого (тип × категория × режим, экспоненциальное затухание по времени) → ранжирование билетов (незнакомая категория со слабым результатом выше; сложность ≈ рейтинг R10 + δ) и статей (по типам ошибок); каждая рекомендация несёт `reason { errorType, count, ruleId }`; повторно выданные и выполненные — понижаются. Метрика SC-008 — `eval_recommender.py` на синтетических историях.
- **Rationale**: требования команды к ML; всё офлайн, воспроизводимо, объяснимо преподавателю (принцип II).
- **Alternatives**: коллаборативная фильтрация — нет данных; LLM-рекомендации — невоспроизводимы.

## Открытые вопросы (не блокируют)

### Решения реализации US5, 2026-09-21 (согласованы с владельцем)

- T054: для автоматически строящегося плана ДДС пересекаются категории плана, категории профиля и группы классификатора, где хотя бы одна служба профиля имеет `notifications.mode` = `mapped` или `card112`. `mode=none` реакцией не является. Сопоставление: `serviceIds` → `reference.services[].classifierName` → `notifications[].service`.
- Если ни у одной службы профиля нет `classifierName`, остаётся фильтр по категориям преподавателя. Это сохраняет районные демо-профили, например Обручевский. Если связь есть, но реакции нет, карточка отбрасывается. Условные реакции считаются возможной реакцией группы; вычисление признаков опросной карты относится к режиму A. В `operator112` фильтр профиля службы не применяется (FR-031).
- Совместимость R20: явное расписание `cardFlow`, выдача конкретной карточки преподавателем и старый путь без `plan` сохраняют семантику мока. Фильтр применяется к автоматическому плану и подбору следующей карточки.
- T051: экспорт по индивидуальному или групповому reportId; студент — только собственный индивидуальный отчёт, преподаватель — только свои занятия, администратор — любые; анониму 401. Одна строка на фактическую попытку, включая незавершённые (неизвестные итоговые значения пусты). Балл учитывает последний override. В тренировке результат «сдал/не сдал» пустой; в экзамене сравнивается с `exam.passThreshold`, без выдуманного порога по умолчанию.
- T052 использует существующую модель `ProfileMappingRow` в `app/models/teacher.py`: `profile`, `group_name`, `service_ids[]` сохраняют фронтовый контракт и существующую схему БД. Дублирующая модель с `service_id/title` не создаётся.
- Проверки Phase 5: контрактные тесты преподавателя/экспорта и unit-тест профилей. Полный `scripts/e2e-teacher.sh` зависит также от сценариев, материалов и админ-аудита фаз 6/8; его общий гейт остаётся в T074. Его категория по умолчанию «пожар в жилом доме» не имеет реакции `Деп. ЖКХ` в текущем классификаторе: при проверке строгой связи профиль Чертаново эту категорию не получает.

### Решения реализации US6, 2026-09-21 (согласованы с владельцем)

- T057: отдельные модели не создавались — `Scenario` и `TrainingMaterial` из `app/models/scenario.py` покрывают контракт; схема БД не менялась. Удаление мягкое (`deleted=true`), 409 `conflict` для `source=template` и сценариев, назначенных в занятия (`sessions.scenario_ids`). Правки накапливаются в `history`, аудит `scenario.update/delete/generate/submit/approve/approvePartial/reject` и `material.upload`.
- Граф валидации: `submit` разрешён из `draft`, `rejected` и `approved` (повторная отправка утверждённого — как в моке, требуется `scripts/e2e-teacher.sh`); `approve`/`approvePartial`/`reject` — только из `pending`, иначе 409. `PATCH` не меняет статус. Отчёт валидатора сохраняется в `scenarios.validation_report` и отдаётся расширением ответа `validationReport` (контракт `Scenario` не нарушен — поле дополнительное).
- Роли — как в US5: `require_teacher_actor` (`app/api/deps.py`) без cookie работает как мок (id из тела/query, иначе 400); с cookie студент → 403, чужой преподаватель → 403, администратор без ограничений.
- T059, классификатор групп ЕКП: эмбеддинги rubert-tiny2 + LogisticRegression (`C=20`, вес карточек 5) на 96 карточках и синтетике из строк `classifier.json` (`data/labeled/synthetic_groups.json`, 2671 образцов, два шаблона). Артефакт `models/ekp_group_lr.joblib` git-ignored — после клона `uv run python -m ml.scripts.train_classifier`; без артефакта — режим прототипов (центроиды групп), без эмбеддингов — лексический режим с `available=false`. Метрики в `var/metrics.json`: accuracy 1,0 на 96 карточках (они в обучении — SC-006 выполнен формально) и 0,57 на 5-блочной кросс-валидации по карточкам; оба числа фиксируются честно, порог «требует ручной проверки» — уверенность < 0,6.
- T060, валидатор: шесть критериев (`category`, `address`, `requiredFields`, `duplicate`, `grammar`, `consistency`), `passed` / `needsReview`. Дедупликация (`ml/nlp/dedup.py`): `multilingual-e5-small`, если скачан (`prepare_models --only dedup`), иначе rubert-tiny2 — на объявленных дублях сидов оба дают 1,0, поэтому e5 для демо не обязателен; порог 0,92; без эмбеддингов — лексический фолбэк с `available=false`. Объявленные связи (`duplicateOf`, `baseCardId`, `fabulaCardId`) исключаются из сравнения. Доменный словарь symspell расширен названиями улиц (иначе «Сумская» → «Сумка»). Приёмка на `data/labeled/tickets/` (20 корректных + 20 дефектных, `build_labeled_tickets`): 20/20 и 20/20.
- T060, генератор: шаблонный путь детерминирован по категории — карточка той же группы + новый адрес из `mocks/local/addresses.json` + ловушка; ловушки по умолчанию `—`, `foreignTerritory`, `operatorMistake` (доступны также `duplicate`, `crossRegion`), эталон `etalon.cards[id]` строится из ожидаемых служб билета и строк классификатора (принцип V). LLM-путь — Ollama (`OLLAMA_URL`, `OLLAMA_MODEL`, `OLLAMA_TIMEOUT_SEC`) с JSON-схемой и ≤ 2 повторами; при любом сбое — шаблонный путь. Заголовки вариаций детерминированы, поэтому повторная генерация по категории возвращает существующие сценарии (дедупликация по `title` в сервисе).

### Решения реализации US10 (волна A), 2026-09-21 (согласованы с владельцем)

- Граница с командой ИИ-агентов: `LocalAiGateway.call_reply` остаётся заглушкой `None`; `POST /calls/reply` сначала опрашивает `get_gateway().call_reply(to_number, turn, context)` с `context = { number: InternalNumber, text, reference }`, при `None` — детерминированный `ml/insights/call_responder.py`. Реализация команды ИИ, подключённая через `set_gateway()`/подкласс, автоматически становится приоритетной; ожидаемый ответ — `CallReply { text, voice, speakerTitle }` (недостающие `voice`/`speakerTitle` дополняются из справочника).
- Ответчик: `answer` → «Слушаю вас» (реплика сидов), `reply` → подтверждение с вариацией по номеру (`CONFIRMATIONS`: 301/302 — реплики сидов, 101–104/112/303 — свои, иначе «Понял, информация принята»); голос по чётности номера (как в моке: 101 female, 102 male); `speakerTitle` из `reference.internalNumbers`.
- Чек-лист доклада: `check_report(transcript, card, statuses, reference)` сверяет реплики диспетчера с фактами карточки — номер карточки (id / «карточка N» / ticketNo), адрес (улица справочника или ≥ 50 % основ слов адреса), тип (группа или фабула ≥ 50 % основ), пострадавшие (упоминание / отрицание), решение (принята / не принята / передано / направлен). Лексически по основам (`ml.nlp.semantic.stems`), без модели — всегда `available=true`. Результат сохраняется в `attempts.calls[i].report` (расширение `PhoneCall`, контракт не меняется — дополнительное поле как `validationReport`).
- Оценка: компонент `ml/assess/components/report.py` при отсутствии `etalon.reportChecklist` берёт сохранённую сверку из звонков (лучший доклад по доле пунктов) и пишет `reportIncomplete` с пропущенными пунктами — спецификация US10 «доклад без номера карточки → в оценке "не назван номер карточки"». Версия оценщика `dds-1.1.0`; метрики размеченной выборки не меняются (в ней нет звонков с `report`).
- Хранение: отдельная таблица `phone_calls` не создаётся — вызовы живут в `attempts.calls` JSON (как `CardEvent.calls` мока); id `call-NNN` по максимальному суффиксу среди всех попыток. `servicesCalled` не трогаем (мок не обновляет; оценщик объединяет `calls` и `servicesCalled`). Студент с cookie пишет вызовы только за себя (403), аноним — как мок.
- Проверки Phase 7: `tests/contract/test_calls.py` (строки 16–17, приоритет шлюза, оценка с `reportIncomplete`) и `tests/unit/test_call_responder.py`.

### Решения реализации US11 (волна A), 2026-09-21

- Модели: `system_settings` остаётся в `app/models/reference.py` (её уже читает политика входа); `app/models/system.py` добавляет `system_services`, `system_logs`, `system_static` (`monitoring`, `usageStats`, `integrity` сида). Сид `mocks/admin/*` грузится в `seed_admin`; `--reset` пересоздаёт таблицы.
- Сервисы: start/stop/restart — переходы состояния в БД с обнулением аптайма (start идемпотентен), процессами не управляем — как мок, честно. Критичный сервис при идущем занятии (`sessions.state=running`) → 409 «Недоступно во время активного занятия…». Каждое действие — `system_logs` (WARN для stop) и аудит `service.action`.
- Самопроверка `integrity`: `SELECT 1`, каталоги `var/backups`, `var/recordings` создаются/проверяются; отсутствие эмбеддера или артефакта классификатора — только пометка в `details` (`ok` не снимается, FR-043), чтобы чистое окружение без моделей проходило `e2e-admin.sh` («4 true»).
- Настройки: патч по секциям, `database` и неизвестные ключи отбрасываются; нормативы — `validate_settings_patch` (дословные сообщения `validation/settings.ts`) → 422 `validationFailed` «Настройки не сохранены. …» со всеми нарушениями через «; ». `security.*` сразу влияет на `/auth/policy` и вход.
- Бэкап: `backup.lastAt` в патче = «Выполнить сейчас» → `services/backup.run_backup` (SQLite — консистентная копия через `sqlite3.Connection.backup`, PostgreSQL — `pg_dump --format=plain` по `DATABASE_URL`) в `VAR_DIR/backups/backup-<UTC>.{db|sql}`. `lastAt` сохраняется как передан (совместимость: e2e читает его обратно). Сбой архива (нет `pg_dump`, БД в памяти) — `ERROR` в `system_logs` и пометка в деталях аудита `backup.run`, ответ остаётся 200 — сохранение настроек не блокируется.
- Пользователи: без cookie и без `adminId` → 400 «Укажите adminId» (как мок), с `adminId` не администратора → 403; viewer-студент/преподаватель на любой `/admin/*` → 403 (SC-013). Временный пароль — `security.temporary_password` (10 символов), `failed_logins` сбрасывается при разблокировке и сбросе пароля; ролевые поля приводятся к роли (`group` только student, `assignedGroups` только teacher, `service` не у admin).
- Аудит: типы событий и названия действий продублированы из `src/shared/config/auditEvents.ts` в `app/schemas/admin.py` (фильтр `type`, поиск `q` по названию/коду/деталям/карточке); `operator` — ФИО/логин/АРМ/`userId`; `from`/`to` датой без времени трактуются как границы суток по Москве включительно; сортировка новые первыми, `PageResponse`.
- Проверки Phase 8: `tests/contract/test_admin.py` — 20 тестов (матрица доступа 2 роли × 7 путей, пользователи, сервисы + блокировка занятием, нормативы настроек, бэкап, мониторинг/статистика, фильтры и пагинация аудита).
