**Feature Branch**: `002-two-mode-simulator`

**Created**: 2026-09-20

**Status**: Draft (v2 — минимум, согласованный с командой 20.09.2026)

**Input**: User description: "начинаем" + минимум по ролям от команды (20.09.2026): оператор 112 принимает аудиозапись происшествия и заполняет карточку; оператор ДДС принимает карточку 112 и принимает решение по службе; преподаватель — аналитика, выбор/случайные билеты, создание билетов (в т. ч. с ИИ); администратор — роли, мониторинг отчётов, безопасность; режим экзамена для обоих операторов; две платформы — «лобби» и «тренажёр» с фронтом реальной системы-112; ML — валидация сгенерированных билетов и рекомендательная система.

**Источники**: `specs/kb/02-requirements.md` (ТЗ), `03-qa-session-summary.md` (Q&A 16.09.2026), `04-domain/*` (памятка АРМ-112, классификатор ЕКП v046_24, 96 билетов), `05-ml-plan.md`, `08-two-modes-model.md`. Заменяет `specs/001-dispatcher-simulator/spec.md`.

## Контекст

Заказчик — ГБУ «Система 112» (Москва). В реальной системе карточка происшествия проходит через двух людей: **специалист-112** принимает звонок и заполняет карточку; она рассылается по списку оповещения, и **диспетчер ДДС** городского хозяйства принимает её и регистрирует реагирование. Тренажёр готовит человека, которого могут направить на практику в любое из двух мест, поэтому у обучаемого одна учётная запись и **два режима задания**: `operator112` (режим A) и `dds` (режим B).

Продукт состоит из **двух платформ** с общим бэкендом:

- **Лобби** — вход, назначенные задания, история попыток, личная аналитика, рекомендации, справочник по ситуациям (что делать при каждом типе происшествия), в перспективе — карта. Дизайн свободный.
- **Тренажёр** — рабочее место обучаемого с интерфейсом реальной системы-112 из памятки (экраны ПОВ-112: карточка, очередь, опросная карта, список оповещения). Внешний вид тренажёра **не меняется** — только то, что есть в памятке.

Фронтенд тренажёра для режима B уже реализован в этом репозитории (Next.js, `src/`, `app/`) на мок-слое `/api/mock/*` с зафиксированным контрактом (`docs/mock-api.md`, `spec/05-data-models.md`, `src/shared/api/types/*`); бэкенд MUST заменить мок-слой без изменения контракта (переключение — `NEXT_PUBLIC_MOCK_API_BASE_URL`). Лобби и режим A во фронтенде отсутствуют — их бэкенд-API проектируется первым, экраны — отдельным треком.

Задания выполняются в **тренировочном** режиме (подсказки, повторы, неограниченные попытки) или в **экзаменационном** (фиксированный набор билетов, без подсказок и повторов, порог «сдал/не сдал»). Преподаватель управляет заданиями и является арбитром авто-оценки. Продукт работает в изолированной сети без интернета.

Термины: **карточка** — карточка происшествия ПОВ-112; **билет** — учебная ситуация (фабула, заявитель, адрес) с эталоном; **режим** — `operator112` / `dds`; **формат** — тренировка / экзамен; **задание** — набор билетов, назначенный преподавателем обучаемому/группе в режиме и формате; **попытка** — отработка одного билета одним обучаемым; **первичное решение** (режим B) — Принята / Не принята с указанием причины и службы, куда передано; **статусы реагирования** — Начало реагирования / Прибытие / Проведение работ / Работы завершены (расширение); **опросная карта** — дерево «тип → признаки» → итоговый тип ЕКП; **список оповещения** — службы, которым карточка рассылается по итоговому типу; **эталон** — правильный результат билета для режима.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Режим диспетчера ДДС: приём карточки и первичное решение (Priority: P1)

Обучаемый открывает задание режима `dds` в тренажёре. В очередь падает карточка 112 (из банка билетов, сгенерированная или сформированная другим обучаемым в режиме A). Обучаемый открывает её за 30 с, читает фабулу, адрес, признаки и список оповещения и принимает первичное решение в блоке своей службы: **«Принята»** (поля «Номер наряда», «Направлены рабочие») или **«Не принята»** с обязательным комментарием «причина + кому передано» и выбором службы, в которую передаётся карточка. Пока он работает, могут падать новые карточки. Часть карточек содержит ловушки: ошибки оператора 112 (неверный тип, адрес с опечаткой или вне зоны обслуживания, дубль) — правильное решение зависит от них. Подтверждение решения завершает попытку.

**Why this priority**: минимум режима B, согласованный командой; эталон выводится из билета и классификатора без ИИ, поэтому цикл «карточка → решение → оценка» замыкается первым.

**Independent Test**: задание `dds` из 3 карточек (профильная, непрофильная, с адресом вне Москвы) для одного обучаемого; обучаемый принимает 3 решения; в журнале все события с таймстампами, попытки переданы на оценку.

**Acceptance Scenarios**:

1. **Given** обучаемому назначено задание `dds`, **When** система выдаёт карточку, **Then** она видна в очереди с таймером «мм:сс» и индикацией «нет решения»; очередь обновляется без перезагрузки страницы.
2. **Given** карточка в очереди, **When** обучаемый открывает её, **Then** в блоке его службы автоматически ставится «Получена службой» с таймстампом.
3. **Given** карточка в очереди, **When** решение не принято за 30 с, **Then** карточка помечается «Не оповещено» (красная индикация), событие записывается; работа остаётся возможной.
4. **Given** карточка открыта, **When** обучаемый выбирает «Не принята», **Then** требуется комментарий и выбор службы-получателя из справочника; без них сохранить нельзя.
5. **Given** обучаемый выбирает «Принята», **When** сохраняет, **Then** доступны и записаны поля «Номер наряда» и «Направлены рабочие»; попытка завершена.
6. **Given** карточка с адресом вне Москвы, **When** обучаемый ставит «Принята», **Then** попытка завершается, а оценка фиксирует ошибку «неверное первичное решение» (см. US2).
7. **Given** обучаемый работает с карточкой А, **When** поступает карточка Б, **Then** таймер Б идёт независимо, переключение между ними не теряет введённого.

### User Story 2 - Автоматическая оценка и разбор попытки в обоих режимах (Priority: P1)

Сразу после завершения попытки система формирует оценку. Режим B: время до открытия и до решения (норматив 30 с), правильность первичного решения относительно эталона, корректность службы-получателя при передаче, наличие и смысловая полнота комментария, распознавание ловушки (ошибка оператора 112, дубль, чужая территория), реакция на параллельные карточки, грамматика ручного ввода. Режим A: правильность итогового типа и признаков опросной карты (и вытекающего списка оповещения), адрес по справочнику улиц (опечатки, похожие названия), полнота описания (не потеряны факты из записи), признаки-кнопки и флаги ЧС/ЧП, заявитель и телефон, время до отправки, грамматика. Обучаемый видит балл 0–100, компоненты, список ошибок с текстом нарушенного правила и, в режиме A, сравнение «моя карточка ↔ эталон» по полям. Преподаватель видит то же и может изменить оценку с комментарием. В экзамене дополнительно выводится «сдал / не сдал» по порогу.

**Why this priority**: «контроль и оценка на основе машинного обучения» — центральный критерий кейса; без оценки ни один режим не замкнут.

**Independent Test**: подать в оценщик 5 размеченных попыток режима B (эталонная, с опозданием, без комментария, «Принята» по чужой территории, неверная служба-получатель) и 5 режима A (эталонная, неверный тип, потерян факт «дом газифицирован», опечатка улицы, не выставлен «пострадавшие») — каждая получает ожидаемый набор ошибок и балл в ожидаемом диапазоне; результат воспроизводим.

**Acceptance Scenarios**:

1. **Given** попытка завершена, **When** оценка рассчитана, **Then** обучаемый видит балл 0–100, компоненты своего режима и ошибки, каждая со ссылкой на правило-источник.
2. **Given** режим B, эталон «карточка-112» для службы обучаемого, **When** поставлено «Не принята», **Then** ошибка «неверное первичное решение» (нарушение №2/№3 памятки) с ожидаемым статусом.
3. **Given** режим B, комментарий «не обслуживаем», **When** эталон требует «причина» и «кому передано», **Then** ошибка «неполный комментарий» (нарушение №5); «территория ЖКХ Басманного района, передано в ОДС-3» засчитывается без побуквенного совпадения.
4. **Given** режим B, карточка с ошибкой оператора 112 (тип «Запах газа», а по фабуле — прорыв трубы), **When** обучаемый принял её как профильную для Мосгаза, **Then** ошибка «не распознана ошибка классификации, ожидалось: Не принята, передано в Мосводоканал».
5. **Given** режим A, введено «ул. Дубнинская» при эталоне «ул. Дубининская», **When** оценка рассчитана, **Then** ошибка «опечатка в адресе, похожая улица» отдельно от грамматических.
6. **Given** режим A, в записи «дом газифицирован», **When** факта нет в описании ни в какой формулировке, **Then** ошибка «потерян ключевой факт»; «в доме газ» засчитывается.
7. **Given** режим A, выбрано «Дом → газовая плита» при эталоне «Запах газа в квартире», **When** оценка рассчитана, **Then** ошибка «неверный итоговый тип» с перечнем служб, не попавших в список оповещения.
8. **Given** экзамен с порогом 70, **When** балл 65, **Then** результат «не сдал», попытка помечена «экзамен» и учтена отдельно в аналитике.
9. **Given** преподаватель меняет балл или снимает ошибку, **When** сохраняет с комментарием, **Then** аудит содержит «кто, когда, что было, что стало, комментарий», обучаемый видит обновлённую оценку, правка попадает в выборку для перекалибровки.
10. **Given** решение принято быстрее настраиваемого порога чтения, **When** оценка рассчитана, **Then** предупреждение «возможное угадывание» без снижения балла по умолчанию.

### User Story 3 - Режим специалиста-112: приём аудиозаписи происшествия и заполнение карточки (Priority: P1)

Обучаемый открывает задание режима `operator112`. Поступает «вызов»: сигнал, АОН заполняется автоматически, создаётся карточка с таймером. Обучаемый отвечает и слышит **аудиозапись обращения заявителя**, сгенерированную из билета (фабула + ФИО + телефон + адрес + уточнения, разговорным языком). В тренировке запись можно прослушать повторно, в экзамене — один раз. Обучаемый заполняет карточку в интерфейсе ПОВ-112: заявитель и статус, адресный блок с подсказкой по справочнику улиц, описание со слов заявителя, признаки-кнопки, флаги ЧС/ЧП, опросная карта → итоговый тип; список оповещения формируется автоматически, службу можно добавить вручную. Нажимает «сохранить»/«отправить» → карточка «Зарегистрирована», попытка завершена. В тренировке доступны подсказки по базовым шагам.

**Why this priority**: второй из двух режимов; 96 билетов написаны именно под него; запись вместо диалога делает режим детерминированным и не зависящим от ИИ-собеседника.

**Independent Test**: задание `operator112` из 2 билетов; обучаемый прослушивает записи, заполняет и отправляет карточки; в попытках есть все поля с историей правок, число прослушиваний, таймстампы ответа и отправки; попытки переданы на оценку.

**Acceptance Scenarios**:

1. **Given** назначено задание `operator112`, **When** система выдаёт вызов, **Then** карточка создаётся с АОН, номером и таймером; сигнал слышен/виден; время ответа фиксируется; неответ за 30 с записывается как событие.
2. **Given** вызов принят, **When** запись воспроизводится, **Then** она содержит все факты билета в разговорной форме; в тренировке доступна кнопка «прослушать ещё раз», число прослушиваний фиксируется; в экзамене кнопки нет.
3. **Given** обучаемый вводит улицу, **When** введено ≥ 3 символов, **Then** предлагаются варианты из справочника; выбор из списка и ручной ввод фиксируются отдельно.
4. **Given** выбрано «Происшествие 101 → Где: Дом → Признак пожара: Дым», **When** выбор завершён, **Then** показан итоговый тип ЕКП и список оповещения по классификатору; удалить службу нельзя, добавить — можно с пометкой «вручную».
5. **Given** карточка заполнена, **When** обучаемый нажимает «сохранить», **Then** статус «Зарегистрирована», блок «Класс.: …», время отправки зафиксировано, попытка завершена и передана на оценку.
6. **Given** тренировка с подсказками, **When** обучаемый 20 с бездействует на этапе, **Then** подсвечивается следующий базовый шаг («заполните адрес»); показ подсказки записан.
7. **Given** аудио недоступно (нет устройства вывода), **When** вызов принят, **Then** обучаемому показана текстовая расшифровка записи с пометкой «аварийный режим», попытка помечена и не блокируется.

### User Story 4 - Лобби обучаемого: задания, история, аналитика, советы, справочник (Priority: P2)

Обучаемый входит в лобби и видит назначенные задания (режим, формат, число билетов, срок), историю попыток с баллами и разборами, личную аналитику (динамика балла по режимам, время реакции, типовые ошибки), рекомендации («повторите категорию “Запах газа”», «прочитайте статью “Адреса: похожие улицы”») и справочник по ситуациям — статьи по типам происшествий (что спросить, что заполнить, кого оповестить, типичные ошибки), выведенные из памятки, классификатора и билетов. Из лобби обучаемый запускает задание — открывается тренажёр. Чужие результаты недоступны.

**Why this priority**: точка входа для обучаемого и место, где живут аналитика и рекомендации — то, что жюри увидит первым после тренажёра.

**Independent Test**: обучаемый с 3 оценёнными попытками видит их в истории, динамику балла, ≥ 1 рекомендацию со ссылкой на статью справочника; статья открывается; чужие попытки не отдаются.

**Acceptance Scenarios**:

1. **Given** обучаемому назначены задания, **When** он открывает лобби, **Then** видит список заданий со статусом (не начато / в процессе / завершено / сдал / не сдал) и кнопку запуска.
2. **Given** есть ≥ 1 оценённая попытка, **When** открыта история, **Then** каждая попытка показывает режим, формат, билет, балл, дату и ссылку на разбор.
3. **Given** есть ≥ 3 попытки, **When** открыта аналитика, **Then** показаны динамика балла по режимам, среднее время реакции и топ-3 типа ошибок.
4. **Given** есть ошибки типа «адрес», **When** открыты рекомендации, **Then** есть рекомендация с ссылкой на статью справочника по адресам и на билеты той же категории.
5. **Given** справочник открыт, **When** выбран тип происшествия, **Then** статья содержит: признаки опросной карты, список оповещения по ЕКП, что уточнить у заявителя, типичные ошибки.

### User Story 5 - Преподаватель: назначение заданий, экзамен и аналитика группы (Priority: P2)

Преподаватель создаёт задание: группа/обучаемые, режим (`operator112` / `dds` / цепочка A→B), формат (тренировка / экзамен), билеты — выбранные вручную из банка или случайные по категориям и сложности (N штук), для экзамена — порог «сдал», лимит времени, для тренировки — подсказки вкл/выкл, темп поступления карточек, веса критериев. Следит за выполнением (кто на каком билете, таймеры, нарушения) и завершает задание. Смотрит аналитику группы: сводная таблица по обучаемым (баллы по режимам, время, ошибки по типам, сдал/не сдал), тепловая карта «категория × тип ошибки», топ ошибок группы с текстовым инсайтом; экспорт CSV/PDF. Правит авто-оценки с комментарием.

**Why this priority**: рабочее место преподавателя и отчёт — главный экран для жюри (преподаватели УМЦ ГО ЧС).

**Independent Test**: преподаватель назначает экзамен `dds` из 5 случайных билетов категории «Водоснабжение» с порогом 70 двум обучаемым; они проходят; в аналитике 10 попыток, по каждому обучаемому «сдал/не сдал», тепловая карта построена, CSV экспортирован.

**Acceptance Scenarios**:

1. **Given** преподаватель создаёт задание `dds`, **When** выбирает категории и профиль службы, **Then** в выборку попадают только билеты, где у службы есть реакция в классификаторе; для `operator112` профиль не запрашивается.
2. **Given** выбран «случайные билеты, N = 5», **When** задание запущено, **Then** каждый обучаемый получает 5 разных билетов выбранных категорий и сложности; в экзамене набор фиксируется при запуске.
3. **Given** задание идёт, **When** преподаватель открывает мониторинг, **Then** состояние каждого обучаемого обновляется не реже раза в 2 с.

### User Story 6 - Преподаватель: создание билетов вручную и с ИИ, валидация и утверждение (Priority: P2)

Преподаватель открывает банк билетов: 96 базовых из учебных билетов с эталонами по классификатору. Создаёт новый билет вручную (фабула, заявитель, адрес из справочника, тип ЕКП — эталон достраивается автоматически) или запрашивает генерацию: категория, локация, сложность, количество, ловушки (ошибка оператора 112, дубль, чужая территория) → система генерирует билеты, **валидирует** каждый (категория подтверждена классификатором, адрес найден в справочнике, обязательные поля заполнены, нет дубликата по смыслу, грамматика чистая, факты фабулы согласованы с типом) и показывает предпросмотр с эталоном и результатом валидации. Эталон для режима B строится по исходному билету: если оператор классифицировал верно — диспетчер профильной службы должен «Принять»; если ошибся — «Не принята» с передачей в профильную службу. **Why this priority**: «сформированные обучающимися карточки» из ТЗ и «обработка ошибок оператора 112» из минимума команды; требует US1 и US3.

**Independent Test**: обучаемый 1 в режиме A отправляет карточку по билету «запах газа» с намеренно неверным типом; обучаемый 2 (профиль Мосгаз) получает её; эталон ожидает «Не принята, передано в Мосводоканал»; в отчёте попытки связаны.

**Acceptance Scenarios**:

1. **Given** задание-цепочка, **When** обучаемый в режиме A отправляет карточку, **Then** в течение 5 с она появляется в очереди обучаемого режима B со службой из списка оповещения и признаком «сформирована обучаемым».
2. **Given** карточка из режима A с ошибочным типом, **When** формируется эталон режима B, **Then** ожидаемое решение — «Не принята», элементы комментария — «не профильное, передано в <служба по билету>».
3. **Given** ни у кого в группе нет службы из списка оповещения, **When** карточка отправлена, **Then** она остаётся в банке задания с пометкой «нет адресата» и видна преподавателю.
4. **Given** преподаватель выпускает «дубль по адресу» обучаемому режима B, **When** карточка поступила, **Then** эталон ожидает «Не принята: дубль, реагирование по КП №…».

### User Story 11 - Администрирование, безопасность и мониторинг отчётов (Priority: P4)

Администратор создаёт учётные записи и роли, объединяет обучаемых в группы, блокирует, видит журнал аудита и отказы в доступе, состояние сервисов (БД, ML-модели, генерация аудио), сводку отчётов по всем заданиям (без права менять оценки и билеты), запускает резервное копирование; задаёт политику паролей и сроки хранения записей.

**Why this priority**: сквозное требование ТЗ; минимально необходимо для демо с тремя ролями.

**Independent Test**: администратор создаёт преподавателя и двух обучаемых в группе; преподаватель видит группу; администратор видит отчёт задания, но не кнопку «изменить оценку».

**Acceptance Scenarios**:

5. **Given** администратор нажимает «Создать резервную копию», **When** операция завершена, **Then** файл доступен, запись в журнале.

### Edge Cases

- Обучаемый закрыл браузер/потерял связь во время попытки → события сохранены на сервере, при возврате в рамках задания попытка продолжается; таймеры — по серверному времени; в экзамене число прослушиваний не сбрасывается.
- Режим A: обучаемый отправил карточку, не дослушав запись → карточка принята, оценка фиксирует потерянные факты; число прослушиваний = 0 отражено в разборе.
- Режим A: запись не сгенерировалась для утверждённого билета → билет не выдаётся в режиме A до появления записи; преподаватель видит предупреждение.
- Режим A: обучаемый добавил службу вручную → фиксируется, не штрафуется и не поощряется по умолчанию.
- Режим B: адрес вне Москвы → эталон «Не принята: не наша территория, передано в 112 региона».
- Режим B: непрофильное/ложное обращение → эталон «Не принята» с причиной; служба-получатель — по классификатору или «нет».
- Режим B: карточка от ВИС без признаков и с пострадавшими только в описании → эталон по описанию; оценка не штрафует за отсутствующие в источнике признаки.
- Режим B: обучаемый поставил «Не принята», затем исправил на «Принята» до подтверждения → засчитывается исправление с задержкой, ошибка помечена «исправлена».
- Экзамен: время вышло до завершения попытки → попытка завершается принудительно, оценивается выполненное, «не сдал» если ниже порога.
- Экзамен: обучаемый пытается запустить второй раз → отказ, преподаватель может разрешить пересдачу явно (новое задание).
- Генератор вернул билет не той категории, дубль или с адресом вне справочника → «не прошёл валидацию» с причинами по критериям; в банк не попадает без ручного исправления.
- Классификатор не уверен в категории билета (низкая уверенность) → валидация «требует ручной проверки», не «отклонено».
- Преподаватель завершил задание, пока обучаемый на середине билета → попытка «прервана», оценивается выполненное; в цепочке неотправленные карточки A в очередь B не попадают.
- Два преподавателя правят одну оценку → последняя побеждает, обе в аудите.
- ML-компонента недоступна → детерминированные компоненты считаются, семантические помечены «недоступно»; рекомендации строятся по детерминированным данным; задание не блокируется.

## Requirements *(mandatory)*

### Functional Requirements

**Платформы, режимы, форматы**

- **FR-001**: Система MUST предоставлять две пользовательские платформы с общим бэкендом: лобби (вход, задания, история, аналитика, рекомендации, справочник) и тренажёр (интерфейс ПОВ-112 по памятке); переход из лобби в тренажёр MUST происходить в рамках одной сессии без повторного входа.
- **FR-002**: Система MUST поддерживать два режима задания — `operator112` и `dds` — в одной учётной записи обучаемого; режим фиксируется в задании, попытке, событии и результате оценки.
- **FR-003**: Система MUST поддерживать два формата задания — тренировка и экзамен. В экзамене: фиксированный набор билетов, зафиксированный при запуске; подсказки и повторное прослушивание отключены; лимит времени; одна попытка на билет; результат «сдал / не сдал» по порогу балла; попытки помечаются и учитываются в аналитике отдельно от тренировочных.
- **FR-004**: Тренажёр MUST отображать карточку с полями ПОВ-112: номер, дата/время, регистратор, таймер, телефоны (АОН, предоставленный, на место), признаки-кнопки, флаги ЧС/ЧП, заявитель и статус, адресный блок (страна … код, описательный адрес), описание (до 1999 символов), опросная карта, список оповещения с блоками служб и полями «Номер наряда» / «Направлены рабочие», статус карточки. Внешний вид MUST соответствовать памятке; в режиме A карточка редактируема, в режиме B — просмотр с редактируемым блоком своей службы.
- **FR-005**: Система MUST записывать каждое действие обучаемого (ответ на вызов, прослушивание, открытие карточки, ввод/изменение поля, выбор в опросной карте, добавление службы, отправка, решение, комментарий, выбор службы-получателя, статус, переключение карточки, показ подсказки, получение сообщения) как событие с серверным таймстампом, «было/стало», режимом и форматом.

**Режим диспетчера ДДС (минимум)**

- **FR-006**: Система MUST вести очередь карточек обучаемого с независимым таймером на каждой, сигналом поступления и обновлением без перезагрузки.
- **FR-007**: Открытие карточки MUST автоматически ставить «Получена службой»; отсутствие первичного решения через 30 с (настраивается) MUST помечать карточку «Не оповещено» и фиксировать событие.
- **FR-008**: Первичное решение MUST быть одним из «Принята» (с полями «Номер наряда», «Направлены рабочие») или «Не принята» (с обязательным комментарием и выбором службы-получателя из справочника служб либо «нет»); подтверждение решения MUST завершать попытку в минимальном режиме.
- **FR-009**: Система MUST поддерживать источники карточек режима B: банк билетов, генерация, карточки обучаемых режима A, карточка «от ВИС» (урезанная), ловушки (ошибка оператора 112, дубль, чужая территория).
- **FR-010**: Система MUST поддерживать вариант «Действия с карточками»: ввод текстового действия свободной формой вместо решения.

**Режим специалиста-112 (минимум)**

- **FR-011**: Система MUST имитировать входящий вызов: сигнал, автоматический АОН, номер происшествия, таймер; время ответа фиксируется; неответ за 30 с (настраивается) фиксируется как событие.
- **FR-012**: Система MUST воспроизводить аудиозапись обращения заявителя, сгенерированную из билета заранее (разговорная форма, все факты билета: фабула, ФИО, телефон, адрес, уточнения); в тренировке повторное прослушивание разрешено и подсчитывается, в экзамене — запрещено.
- **FR-013**: Система MUST хранить для каждого утверждённого билета режима A аудиозапись и её текстовую расшифровку; при недоступности аудио на рабочем месте показывать расшифровку с пометкой «аварийный режим».
- **FR-014**: Обучаемый MUST иметь возможность заполнить карточку с нуля: заявитель и статус, адрес с подсказкой по справочнику улиц (с фиксацией «из справочника / вручную»), описание, признаки-кнопки, флаги ЧС/ЧП, опросная карта.
- **FR-015**: Система MUST по комбинации опросной карты определять итоговый тип ЕКП и формировать список оповещения по классификатору; добавить службу вручную — можно (с пометкой), удалить — нельзя.
- **FR-016**: Отправка карточки MUST переводить её в «Зарегистрирована», фиксировать время и завершать попытку.
- **FR-017**: В тренировке система MUST поддерживать включаемые подсказки (следующий базовый шаг при простое ≥ порога); показы фиксируются и отражаются в разборе без штрафа по умолчанию.

**Билеты, эталоны, валидация**

- **FR-018**: Система MUST хранить билет как исходные данные (фабула, заявитель, телефон, адрес, уточнение, факты, ловушки) + эталон режима A (итоговый тип ЕКП, признаки опросной карты, нормализованный адрес, обязательные факты, признаки-кнопки, флаги, список оповещения) + эталон режима B (главная служба, ожидаемое первичное решение для целевой службы, служба-получатель при передаче, элементы комментария, расписание сообщений о ходе работ, чек-лист доклада) + сложность, категория, источник (билет / вручную / генерация / импорт / обучаемый), статус утверждения, аудиозапись (A).
- **FR-019**: Система MUST строить список оповещения и главную службу по классификатору ЕКП v046_24 (нормализация «карточка -112» ≡ «карточка-112»).
- **FR-020**: Система MUST импортировать 96 задач из учебных билетов как базовые с автоэталоном и дедупликацией.
- **FR-021**: Преподаватель MUST иметь возможность создать билет вручную; эталон достраивается автоматически по указанному типу и адресу, грамматика проверяется.
- **FR-022**: Система MUST генерировать билеты по параметрам (категория, локация, сложность, количество, ловушки) на локальной модели с автоэталоном для обоих режимов.
- **FR-023**: Система MUST валидировать каждый сгенерированный или импортированный билет по критериям: категория подтверждена классификатором (с уровнем уверенности), адрес найден в справочнике, обязательные поля заполнены, нет дубликата по смысловой близости, грамматика чистая, факты фабулы согласованы с типом (например, «пострадавшие» в тексте ↔ признак); результат по каждому критерию MUST быть виден преподавателю; не прошедшие билеты в банк не попадают без ручного исправления.
- **FR-024**: Преподаватель MUST иметь возможность утверждать, править (с проверкой грамматики), перегенерировать по комментарию с историей версий; утверждение билета для режима A MUST запускать генерацию аудиозаписи, которую преподаватель может прослушать и перегенерировать.
- **FR-025**: В задания MUST попадать только утверждённые билеты; карточки обучаемых в цепочке считаются утверждёнными в рамках того же задания.
- **FR-026**: Система MUST поддерживать импорт таблицы «ситуация | адрес» (CSV/XLSX/DOCX-таблица) с превращением в билеты.

**Цепочка режимов и ловушки**

- **FR-027**: Карточка, отправленная в режиме A, MUST быть представима как билет режима B в той же структуре без ручной конвертации, с признаком «сформирована обучаемым» и ссылкой на попытку-источник.
- **FR-028**: Эталон режима B для карточки из режима A MUST строиться по исходному билету: верная классификация → «Принята» для профильной службы; ошибочная → «Не принята», передано в службу по билету.
- **FR-029**: Преподаватель и генератор MUST иметь возможность выпускать карточки-ловушки (ошибка оператора 112 в типе, адресе, зоне; дубль) с эталоном, ожидающим распознавания ловушки.

**Задания и инструменты преподавателя**

- **FR-030**: Преподаватель MUST иметь возможность создать задание: группа/обучаемые, режим (`operator112` / `dds` / цепочка), формат (тренировка / экзамен), билеты — выбранные вручную или случайные по категориям/сложности (N), профиль службы (для B), темп поступления, нормативы (30 с; для расширения B — 3 мин), веса критериев, подсказки (тренировка), порог и лимит времени (экзамен), срок выполнения.
- **FR-031**: Система MUST фильтровать билеты режима B по профилю службы (есть реакция в классификаторе); режима A — по категориям.
- **FR-032**: Система MUST показывать преподавателю мониторинг задания (обучаемый, режим, текущий билет, таймеры, очередь, нарушения) с обновлением не реже раза в 2 с и «табло класса» без управления.
- **FR-033**: Преподаватель MUST иметь возможность выпустить обучаемому событие во время задания (дубль, карточка от ВИС, ловушка, сообщение о ходе работ) и завершить задание в любой момент.
- **FR-034**: Система MUST формировать отчёт по заданию: по обучаемому — ФИО, АРМ, режим, формат, времена по этапам и отклонения, ошибки по типам, балл, сдал/не сдал; по группе — сводные диаграммы, тепловая карта «категория × тип ошибки», топ ошибок с инсайтом; экспорт CSV и PDF.

**Оценка**

- **FR-035**: Оценка попытки режима B MUST раскладываться на компоненты: (a) время до открытия и до решения; (b) правильность первичного решения; (c) корректность службы-получателя при передаче; (d) наличие и смысловая полнота комментария; (e) распознавание ловушки; (f) реакция на параллельные карточки; (g) грамматика; при включённом расширении — (h) последовательность, полнота и своевременность статусов; (i) доклад по чек-листу. Веса настраиваются, значения по умолчанию заданы.
- **FR-036**: Оценка попытки режима A MUST раскладываться на компоненты: (a) время ответа и время до отправки; (b) итоговый тип и признаки опросной карты (и список оповещения); (c) адрес — справочник, опечатки, похожие названия; (d) полнота описания — обязательные факты в любой формулировке; (e) признаки-кнопки и флаги; (f) заявитель и телефон; (g) грамматика; (h) число прослушиваний и подсказок — информационно. Веса настраиваются, значения по умолчанию заданы.
- **FR-037**: Каждая ошибка MUST содержать тип (7 нарушений памятки для режима B или типология команды для режима A), пояснение, ссылку на правило-источник, шаг таймлайна, признак «исправлена».
- **FR-038**: Сравнение свободного текста с эталоном MUST быть смысловым, не побуквенным.
- **FR-039**: Адреса ручного ввода MUST проверяться по справочнику улиц Москвы; похожие названия — отдельный тип ошибки.
- **FR-040**: Разбор попытки MUST показывать таймлайн с подсветкой шагов и текстом правил; в режиме A — сравнение карточки с эталоном по полям; в экзамене — «сдал / не сдал».
- **FR-041**: Преподаватель MUST иметь возможность изменить авто-оценку (балл, снять/добавить ошибку) с обязательным комментарием; изменение — в аудит и в выборку для перекалибровки.
- **FR-042**: Система MUST помечать признаки угадывания предупреждением без изменения балла по умолчанию.
- **FR-043**: При недоступности ML-компонент система MUST считать детерминированные компоненты и помечать остальные «недоступно», не блокируя задание.

**Лобби, аналитика, рекомендации, справочник**

- **FR-044**: Лобби MUST показывать обучаемому назначенные задания со статусом, историю попыток с разборами, личную аналитику (динамика по режимам, время реакции, топ ошибок) — только свои данные.
- **FR-045**: Система MUST собирать аналитику по каждой попытке: времена по этапам, баллы по компонентам, ошибки по типам и категориям, число прослушиваний и подсказок, формат, режим; агрегировать по обучаемому, группе, категории, режиму и формату.
- **FR-046**: Система MUST предоставлять справочник по ситуациям: статья на тип/категорию происшествия (признаки опросной карты, список оповещения по ЕКП, что уточнить у заявителя, ожидаемое решение ДДС, типичные ошибки), выведенная из памятки, классификатора и билетов; преподаватель может править статьи.
- **FR-047**: Рекомендательная система MUST по истории попыток формировать обучаемому персональные рекомендации: билеты/категории для повторения, статьи справочника, сравнение режимов («сильнее в A/B»); каждая рекомендация — с причиной (тип и число ошибок) и ссылкой на правило.
- **FR-048**: Система MUST вести рейтинг обучаемого по режимам и сложность билета; в тренировке с адаптивным подбором выбирать следующий билет по правилу «справляется — усложняем, не укладывается — упрощаем и повторяем категорию с ошибками».
- **FR-049**: Система MUST формировать преподавателю групповые инсайты (доля обучаемых × тип ошибки) и предлагать категорию для следующего задания.

**Расширение ДДС и голосовые собеседники**

- **FR-050**: При включённом расширении режима B система MUST выдавать сообщения о ходе работ по расписанию билета и допускать статусы реагирования только в порядке памятки; «Работы завершены» закрывает карточку; норматив полной отработки — 3 мин.
- **FR-051**: Система MUST предоставлять браузерный софтфон для доклада руководителю с ИИ-ответчиком, локальным распознаванием речи и сверкой с чек-листом; при недоступности микрофона — текстовый доклад.
- **FR-052**: Система MUST поддерживать интерактивного ИИ-заявителя (текст/голос) как опциональную замену статичной записи в режиме A, отвечающего строго данными билета.

**Роли, безопасность, эксплуатация**

- **FR-053**: Система MUST аутентифицировать по логину/паролю и разграничивать доступ по трём ролям; администратор MUST NOT менять оценки и билеты.
- **FR-054**: Система MUST вести журнал аудита (действия обучаемых, правки оценок, административные действия, отказы в доступе) с фильтрацией по пользователю и периоду.
- **FR-055**: Администратор MUST иметь возможность управлять учётными записями, ролями, группами, блокировкой, политикой паролей; видеть состояние сервисов, сводку отчётов по всем заданиям (только чтение); запускать резервное копирование.
- **FR-056**: Система MUST работать полностью офлайн: модели, справочники и аудиозаписи поставляются с дистрибутивом; в рантайме нет внешних обращений.
- **FR-057**: Система MUST поставляться с инструкцией офлайн-установки, синтетическими данными для демо обоих режимов и командой однократной подготовки (модели, классификатор, справочник улиц, билеты, аудиозаписи).

**Совместимость с существующим фронтендом**

- **FR-059**: Бэкенд MUST реализовать все эндпоинты мок-слоя фронтенда (`docs/mock-api.md`: auth, reference, classifier, cards и действия по карточке, attempts, calls, scenarios, materials, profile-mapping, grammar-check, sessions и лента/управление занятием, users, reports, admin/*) с теми же путями, формами запросов/ответов, кодами и форматом ошибок `{ error: { code, message } }`; контрактные тесты фронтенда (`src/shared/api/mock/__tests__/contracts.test.ts`, `scripts/e2e-*.sh`) MUST проходить против бэкенда.
- **FR-060**: Сид-данные бэкенда MUST совпадать с `spec/mocks/*.json` (пользователи, справочники, классификатор, 96 карточек, сценарии, занятие-пример, отчёты) так, чтобы демо-путь фронтенда воспроизводился без правок; расхождения фиксируются в плане как миграции.
- **FR-061**: Точки «ИИ-модуль: заменить на реальный сервис» (`AiGateway`: оценка попытки, проверка грамматики, генерация сценариев, реплики ИИ-абонента, инсайты группы) MUST быть реализованы реальными локальными компонентами; ответы сохраняют форму `AiResponse`/`Evaluation` и остаются помеченными как сгенерированные системой.
- **FR-062**: Сессия фронтенда (cookie `arm112_session` с `AuthSession`) MUST приниматься бэкендом; `token` MUST быть проверяемым (подписанным) вместо мок-токена; изоляция данных по ролям (T2.5-01) MUST выполняться на бэкенде.
- **FR-063**: Новые возможности спецификации, отсутствующие во фронтенде (режим `operator112`, экзамен, лобби, справочник, рекомендации, валидация билетов), MUST добавляться новыми эндпоинтами и полями, не ломая существующий контракт.

### Key Entities *(include if feature involves data)*

- **Пользователь**: логин, ФИО, роль, номер АРМ, профиль службы (B), группа, блокировка.
- **Группа**: название, куратор, обучаемые.
- **Справочник ЕКП**: группа → признаки → итоговый тип (1283) → главная служба → реакции служб (85).
- **Справочник служб**: код, название, профиль (для выбора службы-получателя и профиля обучаемого).
- **Справочник улиц**: нормализованное название, тип, округ/район.
- **Билет**: исходные данные + эталон A + эталон B + ловушки + категория + сложность + источник + статус утверждения + версии + аудиозапись с расшифровкой.
- **Статья справочника**: тип/категория ЕКП, разделы (признаки, оповещение, что уточнить, решение ДДС, типичные ошибки), правки преподавателя.
- **Задание**: преподаватель, группа/обучаемые, режим, формат, билеты (список или правило случайного выбора), параметры (профиль, темп, нормативы, веса, подсказки, порог, лимит времени, срок), статус, времена.
- **Попытка**: обучаемый × билет × задание × режим × формат; статус; события; карточка; результат оценки; число прослушиваний; связь с попыткой-источником/порождённой карточкой.
- **Карточка**: экземпляр ПОВ-112 в попытке (поля FR-004), статус, список оповещения с блоками служб, решение, служба-получатель.
- **Событие**: попытка, тип, «было/стало», серверный таймстамп.
- **Сообщение о ходе работ**: попытка B (расширение), тип, время, ожидаемый статус.
- **Результат оценки**: попытка, версия оценщика, компоненты с баллами и весами, ошибки, предупреждения, балл, сдал/не сдал, флаг «изменено преподавателем».
- **Правка оценки**: результат, преподаватель, было/стало, комментарий, время.
- **Рейтинг обучаемого**: значения по режимам, история, слабые категории.
- **Рекомендация**: обучаемый, тип (билет / категория / статья / режим), причина, ссылка на правило, дата, принята ли.
- **Отчёт по заданию**: агрегат по попыткам; представления CSV/PDF.
- **Запись аудита**: пользователь, действие, объект, время, детали.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В режиме B обучаемый принимает решение по карточке от поступления до подтверждения за ≤ 1 минуту без подсказок разработчика; 0 недопустимых состояний в журнале тестового прогона.
- **SC-002**: В режиме A обучаемый прослушивает запись и отправляет корректную карточку по билету за ≤ 5 минут; все поля эталона заполнимы через интерфейс тренажёра.
- **SC-003**: Оценщик режима B на ≥ 50 размеченных попытках: согласие по наличию ошибки каждого типа ≥ 85 %, корреляция балла с экспертным ≥ 0,8; метрики воспроизводятся скриптом.
- **SC-004**: Оценщик режима A на ≥ 30 размеченных карточках: согласие по типу ошибки (тип ЕКП, адрес, потерянный факт, признаки) ≥ 85 %; метрики воспроизводятся скриптом.
- **SC-005**: Валидация сгенерированных билетов на 40 билетах (20 корректных, 20 с внесёнными дефектами): дефектные отклоняются ≥ 90 %, корректные проходят ≥ 85 %.
- **SC-006**: Классификатор категории ЕКП по тексту фабулы даёт accuracy ≥ 80 % на 96 задачах билетов.
- **SC-007**: Аудиозапись обращения на 20 билетах содержит все факты билета (проверка командой по расшифровке — 0 потерянных фактов) и генерируется ≤ 1 мин на билет на сервере без GPU.
- **SC-008**: Рекомендации на 10 синтетических историях обучаемых: в топ-3 присутствует категория с наибольшим числом ошибок в 100 % случаев; каждая рекомендация имеет причину.
