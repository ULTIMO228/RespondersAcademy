# Конституция проекта «Тренажёр специалиста системы-112 и диспетчера ДДС»

Кейс 09 хакатона ЛЦТ 2026, команда 82. Конституция фиксирует принципы, которые
не пересматриваются в рамках отдельной фичи. Источники: ТЗ, Q&A-сессия с заказчиком
16.09.2026, памятка «Работа на АРМ-112», модель двух режимов обучаемого
(`docs/08-two-modes-model.md`) — см. `specs/kb/`.

## Core Principles

### I. Локальный контур и CPU-only (NON-NEGOTIABLE)

Итоговый прототип MUST работать в изолированной локальной сети без интернета
на типовом офисном ПК без GPU. Все модели (эмбеддинги, STT/TTS, LLM, грамматика)
MUST скачиваться один раз на этапе установки и работать офлайн. Внешние API
(облачные LLM, онлайн-геокодеры, онлайн-проверка орфографии) в рантайме запрещены;
облако допустимо только как инструмент разработки (генерация синтетики, эксперименты).
Каждая ML-компонента MUST иметь задокументированный бюджет: размер на диске и
время отклика на CPU.

*Обоснование:* прямое требование ТЗ и Q&A («GPU не предоставляется, проверка на
типовых офисных ПК»). Нарушение = прототип не запустится у экспертов.

### II. Методическая достоверность выше технической новизны

Каждое правило авто-оценки MUST ссылаться на источник: пункт памятки АРМ-112,
строку классификатора ЕКП, норматив из Q&A (30 с / 3 мин) или явное решение
команды, зафиксированное в спецификации. Для режима специалиста-112 источник
эталона — билет + классификатор ЕКП + справочник улиц; для режима диспетчера ДДС —
семь нарушений отдела контроля реагирования из памятки (стр. 26–31) + тайминги.
Каждая найденная ошибка обучаемого MUST быть объяснима преподавателю в одну строку
(«нет комментария к статусу "Не принята" — памятка, нарушение №4»). Преподаватель —
арбитр: он MUST иметь возможность изменить любую авто-оценку, и каждое изменение
MUST попадать в журнал аудита и в выборку для перекалибровки.

*Обоснование:* жюри — преподаватели УМЦ ГО ЧС, а не ИТ-специалисты; критерий
экспертизы «рекомендации сервиса соответствуют реальным».

### III. Измеримый ML

Каждая обучаемая или калибруемая компонента MUST иметь метрику на размеченной
выборке (accuracy / F1 / каппа Коэна / корреляция с экспертной оценкой) и
воспроизводимый скрипт её расчёта. Итоговая оценка карточки MUST раскладываться
на детерминированные компоненты (тайминги, статусы, поля, комментарии, грамматика)
с настраиваемыми весами; LLM-as-judge допускается только как второй эшелон для
спорных случаев и MUST быть отключаем. Модели не обучаются «с нуля»: используются
малые предобученные модели + дообучение/калибровка на билетах и синтетике.

*Обоснование:* критерии экспертизы «проверка расчётов и достоверность»;
Q&A: «сравнение смысловое, не побуквенное», «система учитывает правки преподавателя».

### IV. Простота и приоритет демонстрируемого ядра (YAGNI)

Разработка идёт 15–29 сентября 2026. Порядок работ MUST следовать приоритетам
пользовательских историй спецификации: сначала полный замкнутый цикл одного режима
обучаемого (назначение → отработка → авто-оценка → отчёт), затем второй режим и
связка «карточка из режима A → очередь режима B», затем всё остальное.
Нефункциональные требования ТЗ, не проверяемые на защите (100 пользователей, TLS,
бэкапы по расписанию, горизонтальное масштабирование, восстановление сессий),
MUST быть описаны в архитектуре и документации, но NOT реализуются, если не нужны
для демо. Любая абстракция, не обслуживающая хотя бы одну историю текущей
спецификации, отклоняется. Демо MUST воспроизводиться на синтетических данных без
ручной подготовки и MUST быть записано скринкастом ≤ 5 минут.

*Обоснование:* две недели, пять человек, рекомендация ментора о видео-страховке.

### V. Единый контракт данных между ролями

Точка стыка команды (ИИ-инженер ↔ ML ↔ бэкенд ↔ фронт) — JSON-схемы четырёх
сущностей: **сценарий** (карточка + эталон), **событие обучаемого** (действие с
таймстампом), **результат оценки** (компоненты, ошибки с привязкой к правилу,
итоговый балл), **отчёт по занятию**. Сценарий, событие и результат оценки MUST
нести поле режима `operator112 | dds`; карточка, сохранённая обучаемым в режиме A,
MUST быть представима как сценарий режима B в той же схеме без ручной конвертации.
Схемы MUST лежать в репозитории, быть версионированы и изменяться только через
правку схемы и уведомление команды — не устно. Все эталоны MUST выводиться из
классификатора ЕКП v046_24 и билетов (96 задач), а не придумываться.

*Обоснование:* параллельная работа пяти человек; см. `docs/05-ml-plan.md`
«Точка стыка — JSON эталона и JSON результата оценки» и `docs/08-two-modes-model.md`
«выход режима A — вход режима B».

## Технологические ограничения

- Веб-сервис; браузеры Chrome / Firefox / Яндекс.Браузер; ОС Windows 10/11, Ubuntu 20.04+.
- СУБД: PostgreSQL 12+. Форматы: JSON (сценарии, события, логи), CSV (экспорт отчётов), WAV/MP3 (записи докладов), PDF (отчёты/сертификаты).
- Бэкенд и ML: Python 3.11+. Фронтенд: web SPA (конкретный фреймворк фиксируется в плане фичи).
- Аутентификация: логин/пароль, три роли (администратор, преподаватель, обучающийся), RBAC.
- Данные: только обезличенные материалы организаторов и синтетика. Персональных данных реальных людей в репозитории и демо MUST NOT быть.
- Код открытый, необфусцированный, с комментариями в нетривиальных местах и перечнем зависимостей (требование сдачи).

## Рабочий процесс и качество

- Движок оценки и парсеры данных (классификатор, билеты) MUST покрываться автотестами (pytest); фронтенд и интеграции — минимум ручной чек-лист демо-пути.
- Каждая пользовательская история MUST быть демонстрируема отдельно на синтетических данных (условие приёмки в spec.md).
- Перед сдачей MUST существовать: инструкция по установке офлайн, описание методов обработки данных и метрик, функциональная и компонентная архитектура (требование платформы хакатона).
- Изменения оценок преподавателем, действия администратора и все действия обучаемого MUST логироваться (аудит из ТЗ).

## Governance

Конституция имеет приоритет над spec.md, plan.md и tasks.md любой фичи. Конфликт
с принципом MUST разрешаться правкой артефакта фичи, а не переинтерпретацией
принципа. Изменение самой конституции — отдельным явным решением команды с
повышением версии (MAJOR — удаление/переопределение принципа, MINOR — новый
принцип или существенное расширение, PATCH — уточнение формулировок).
`/speckit-analyze` и `/speckit-plan` MUST проверять соответствие принципам I–V.
