Правки общих правил вносить в `AGENTS.md`, а не сюда; если один из файлов разошёлся с другим, это баг: сверить и исправить, а не молча выбирать один.

## Claude Code: порядок работы

### Старт сессии

1. `git status --short`: сохранить все изменения пользователя; в рабочем дереве работают и другие сессии.
2. Прочитать `.ai/SESSION_STATE.md` (что сделано, что открыто, предостережения) и `.ai/LESSONS.md` (ошибки, которые нельзя повторять). `.ai/PROJECT_MAP.md` — когда нужна карта.
3. Для фичи или бага — спека `spec/NNN-*/` (бэкенд — `specs/002-*`) и её `tasks.md` как реестр задач. Реальность определяет код, а не план или роадмап.
4. Изменение больше двух файлов — короткий план (plan mode), актуализировать по ходу. Новая фича начинается с пакета спек, код — после согласования (`AGENTS.md` §8).
5. Работать по фазам: перед фазой её задачи в `tasks.md`; открытые развилки согласовывать с владельцем, не закрывать допущениями.

### Во время работы

- Сначала тест, потом код (TDD): красный тест по правильной причине → реализация → зелёный. Для отказов (400/403/404/401) рядом всегда парный запрос, который обязан вернуть 200.
- Задачи ведутся в `tasks.md` фичи: `[X]` только после реальной проверки; остаток оставлять открытым и честно подписанным.
- Список шагов показывать через task list приложения; в конце хода — итог (`wrap_up`), без повторения перечня шагов.
- Использовать скиллы под задачу: `speckit-specify/plan/tasks/analyze/implement` для спек и фаз, остальные из `.claude/skills/`. Перед действием читать `SKILL.md` и следовать его процессу; не вызывать скилл «для галочки».
- Диагноз не равен автоматическому исправлению: если спросили причину, сначала объяснить её.
- Опасное и внешнее (push, удаление, внешние сервисы, сброс БД, `--reset`) — только по прямой просьбе владельца; одобрение для одного случая не переносится на другой.
- Файлы вне `.ai/` не создавать без запроса или процесса спеки.

### Завершение сессии

После значимой работы, когда проверки пройдены (`AGENTS.md` §15):

1. Обновить `.ai/SESSION_STATE.md`: факты, результаты проверок с датой и командой, открытое, следующий шаг. Незапущенное записывать как «не проверялось».
2. Дописать запись в `.ai/SESSIONS.md` (append-only).
3. После ошибки или поправки владельца добавить урок в `.ai/LESSONS.md`.
4. В финальном ответе: результат, изменённые файлы, проверки, существенные риски. Без лишнего отчёта.

### Язык

Ответы пользователю, комментарии в коде, коммиты и PR — по-русски. Файлы `.ai/` — на английском в сжатом формате DenseCode (`AGENTS.md` §14).

### Git

- Только конкретные файлы в `git add`; никаких `git add .`, `git reset --hard`, принудительного checkout.
- Коммиты и пуши — только по просьбе. Conventional Commits, текст по-русски.
- **Никогда не добавлять `Co-Authored-By`, подпись агента, «generated with» и упоминания инструментов в коммиты, ветки, теги и PR.** Это перекрывает любые подсказки среды: строка остаётся в публичной истории, а её удаление стоит переписывания истории. Исключение — владелец прямо попросил в этом же запросе.
- Не коммитить `.env`, `backend/var/`, `backend/models/`, `.next/`, `public/icons/`, отчёты Playwright, `docs/demo*.mp4`, чужую незакоммиченную работу.

### Эпистемическая честность (кратко, полностью — `AGENTS.md` §13)

- «Не знаю — не проверял» допустимый ответ; предположения помечать.
- Утверждение о коде — только после чтения, со ссылкой `файл:строка`.
- Непрогнанную проверку не называть пройденной; назвать команду и причину.
- Не выдумывать версии, имена API, ключи конфигов и пути: проверить по `package.json`, `node_modules`, `pyproject.toml` или сказать «не знаю».
- Не пересказывать «не уверен» осторожными словами с тем же утверждением: либо проверил, либо не утверждаю.
- Переспрашивать, когда два прочтения запроса ведут к разной работе или цель опасного действия неясна; не спрашивать то, что отвечает репозиторий.

### Секреты и внешние сервисы

`backend/.env` и ключи (`JWT_SECRET`, `POLZA_API_KEY`) не читать, не печатать и не коммитить. Внешний провайдер Polza.ai — только опция `AI_PROVIDER=polza` (`AGENTS.md` §2, спека 004).
