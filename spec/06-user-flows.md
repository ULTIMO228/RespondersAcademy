# 06. Пользовательские сценарии (flows)

Основание: ТЗ §10 (три сценария), Q&A в4, в6, в8, в9. Каждый сценарий — пошагово, с привязкой к экранам `04-pages/*` и данным `05-data-models.md`.

## Сценарий А. Настройка учебной среды (Преподаватель)

Цель: подготовить эталоны и ролевую модель перед занятием.

1. Вход в систему через защищённый интерфейс локального контура (`/login` → роль teacher).
2. Выбор категории событий по теме занятия (ДТП, пожары, медицина и пр.) — `/teacher/scenarios`: фильтр по категориям ЕКП (настройка «нейросети на генерацию конкретных типов происшествий» — в тестовом фронте: выбор категорий + кнопка «Сгенерировать (ИИ)», возвращающая мок-сценарии).
3. Формирование «эталона»: система автоматически формирует эталонные ответы (из `Etalon` мока) для сравнения с действиями обучающегося.
4. Подтверждение эталонов преподавателем — частичное или полное (`validation.status: approved`, можно утвердить выборочно по полям).
5. Настройка ролевой модели (параллельно): распределение прав обучающихся так, чтобы в их ленту попадали только профильные события (Мосводоканал, Москоллектор, управы, службы газа…) — привязка `User.service` → категории/службы ЕКП.
6. Предпросмотр: преподаватель видит генерируемые вопросы/варианты действий с подсветкой правильных по мнению системы (подсветка из `Etalon.keyPhrases` / `expectedActions`).
7. Коррекция (при необходимости): контекстное поле комментария к вопросу/ответу (`validation.comment`) — «должен быть отработан системой» (в моке: статус `rejected`/`pending` + запись в журнал).
8. Обучение (при необходимости): загрузка материалов в базу (загрузка файлов-заглушек DOCX/PDF/MP3 — ТЗ §12).
9. Проверка грамматики (при необходимости): принудительная проверка после ручных правок (кнопка «Проверить грамматику» → мок-результат с подсветкой).

Экраны: `11-teacher-scenarios.md`.

## Сценарий Б. Практическое занятие на АРМ-112 (карточки)

Участники: Преподаватель + Обучающиеся.

1. Вход участников (`/login`; обучающийся → `/arm`, преподаватель → `/teacher/session`).
2. Преподаватель выбирает категории событий (множественный выбор).
3. Преподаватель инициирует старт занятия (`Session.state: running`).
4. Система имитирует «звонок участника событий»: у обучающегося появляется новая карточка в списке (`CardFlowItem.issuedAt`) + звуковой/визуальный сигнал поступления; старт таймера первичной реакции **30 сек**.
5. Обучающийся открывает карточку (статус службы «Получена службой» — автоматически) и заполняет её в имитации интерфейса АРМ-112: читает блоки, вводит текст в разрешённые поля, проставляет статусы реагирования (полный цикл до «Работы завершены»/«Отказ…»), при необходимости звонит точке C через софтфон. Таймер полной отработки **3 мин**.
6. Во время отработки в очередь поступают новые карточки (многозадачность, Q&A в6) — индикация в списке, нельзя «залипать» на одной.
7. Преподаватель завершает занятие (`state: finished`, в любой момент).
8. Преподаватель формирует отчёт о занятии: действия, замечания (ошибки), время заполнения карточки, отклонение от нормативного, грамматика (`/teacher/reports/[sessionId]`, модель `SessionReport`).

Экраны: `12-teacher-session.md`, `01-arm-main.md`, `02-arm-card.md`, `03-arm-softphone.md`, `13-teacher-reports.md`.

## Сценарий В. Практическое занятие на АРМ-112 (действия с карточками)

Отличия от сценария Б:

- На шаге 2 дополнительно выбирается **категория вопросов** (`Session.cardSource`):
  - сгенерированные системой карточки (`generated`);
  - сформированные обучающимися карточки (`studentCreated`);
  - смешанный выбор (`mixed`).
- Система формирует курсанту **случайную карточку**; после завершения действий с карточкой (включая ввод текста вида «Сообщение принято, дежурная бригада направлена на место») выдаётся **новая карточка**, пока занятие не завершено преподавателем (конвейер без фиксированного числа карточек).
- Остальное (отчёт) — как в сценарии Б.

## Демо-путь для защиты (≤ 5 минут, Q&A в12)

Сквозной путь для скринкаста и живой демонстрации на моках. Учебный датасет моков: 96 карточек из 32 билетов (c-001..c-096, по 3 ситуации на билет — `mocks/cards.json`); сценарии s-001..s-032 собраны по билетам, s-033..s-036 — advanced-вариации (`mocks/scenarios.json`).

1. (0:00–0:30) Вход преподавателем → предпросмотр сценария s-032 «ДТП с разливом топлива и пострадавшими» (билет 32.2, карточка c-095; типовой сценарий заказчика, Q&A в3) с эталоном, утверждение.
2. (0:30–1:00) Настройка занятия: категории [ДТП, Горхоз], группа из 3 курсантов, старт.
3. (1:00–3:30) Вход обучающимся → поступление карточки c-095 (таймер 30 сек) → открытие → проставление статусов полного цикла → звонок точке C (внутренний номер 301, ИИ-абонент «Слушаю вас» → «Я вас понял, информация принята») → ввод текста с опечаткой (демонстрация проверки грамматики) → «Работы завершены».
4. (3:30–4:30) Параллельно: мониторинг преподавателя (экран курсанта), поступление второй карточки (многозадачность).
5. (4:30–5:00) Завершение занятия → отчёт: тайминги и отклонения, 1 грамматическая ошибка, интегральный балл, график; экспорт PDF.

## Состояния и ошибки (обязательны к показу в каждом flow)

- пустой список карточек («Карточек нет»); загрузка; сбой сети ≤ 30 сек с восстановлением без потери ввода (ТЗ §7 — буферизация в localStorage);
- истёк таймер 30 сек → карточка помечается нарушением (аналог «Не оповещено»), фиксация в отчёте;
- попытка сохранить «Не принята»/«Отказ…» без комментария → блокирующая валидация (памятка стр. 26);
- выбор статуса не по порядку → недоступные пункты дропдауна (последовательность из `05-data-models.md`);
- открытие чужого раздела → 403; истёкшая сессия → `/login`.
