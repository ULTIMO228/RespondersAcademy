# 03. Архитектура тестового фронта (Next.js + TypeScript)

## Стек-ориентир

- **Next.js (App Router) + TypeScript** — единое приложение для всех трёх ролей.
- **Feature-Sliced Design**: код организован слоями `app / pages / widgets / features / entities / shared` в `src/`; норматив — `10-code-rules.md` и `hack/Фронт/ПРАВИЛА-КОДА-ФРОНТ.md`. Роуты Next.js (корневой `app/`) тонкие: страницы-роуты только реэкспортируют слайсы FSD-слоя `src/pages/`.
- Мок-слой: **Route Handlers** (`app/api/mock/*/route.ts`), читающие JSON из `spec/mocks/` (или скопированные в `mocks/` внутри приложения), + клиентский data-access слой. Замена на реальный бэкенд = замена базового URL/реализации data-access, контракты из `05-data-models.md` не меняются.
- Рендеринг: серверные компоненты для списков/отчётов; клиентские — для интерактива (таймеры, карточка, софтфон, мониторинг).
- Локализация: вся строковая литеральная база — русская (ТЗ §8).
- Без внешних CDN/шрифтов/аналитики — локальный контур (ТЗ §3, Q&A в11). Все ассеты локальные.

## Мок-слой API (черновые контракты)

Транспорт — JSON (ТЗ §12). Префикс `/api/mock/`. Каждый endpoint читает файлы `spec/mocks/*.json` и применяет минимальную логику (фильтры, пагинация, тик таймера).

| Endpoint | Данные | Потребитель |
|---|---|---|
| `POST /api/mock/auth/login` | users.json | вход |
| `GET /api/mock/cards?status=&type=&q=` | cards.json | главный экран АРМ |
| `GET /api/mock/cards/[id]` | cards.json | карточка |
| `POST /api/mock/cards/[id]/status` | проставление статуса реагирования + комментарий | карточка |
| `POST /api/mock/cards/[id]/links` | связи карточек (read-only проекция допустима) | карточка |
| `POST /api/mock/cards/[id]/worklines` | отработки | карточка |
| `POST /api/mock/cards/[id]/reminders` | напоминания | карточка |
| `GET/POST /api/mock/cards/[id]/sms` | SMS-переписка по карточке | карточка |
| `GET /api/mock/cards/[id]/recordings` | записи разговоров | карточка |
| `GET /api/mock/classifier?group=` | classifier.json | опросная карта, конструктор сценариев |
| `GET /api/mock/reference` | reference.json | все селекты (службы, статусы, округа) |
| `GET/POST /api/mock/scenarios` | scenarios.json | преподаватель |
| `POST /api/mock/scenarios/[id]/validate` | утверждение эталона | преподаватель |
| `GET/POST /api/mock/sessions` · `POST /[id]/start` · `POST /[id]/stop` | sessions.json | проведение занятия |
| `GET /api/mock/sessions/[id]/feed` | поток событий занятия (новые карточки, действия курсантов) | мониторинг |
| `GET /api/mock/reports?sessionId=` | reports.json | отчёты |
| `GET /api/mock/attempts/[id]/evaluation` | оценка попытки (ИИ + правки преподавателя) | прогресс, отчёты |
| `GET /api/mock/admin/*` | users.json, журналы | админка |

Реальное время в тестовом фронте: `sessions/[id]/feed` — long-poll или Server-Sent Events с шагом 2–5 сек; допустимо эмулировать тиками на клиенте по `startedAt`.

### Учебный датасет

- `mocks/cards.json` — учебный датасет: 96 карточек из билетов (все типовые ситуации занятий);
- `mocks/fixtures/arm-cards.json` — UI-фикстуры рабочей карточки ПОВ-112 для экрана карточки (`04-pages/02-arm-card.md`): связи, отработки, напоминания, SMS, записи разговоров.

## Сбой сети («потеря соединения», ТЗ §7)

- Баннер «Потеря соединения» поверх интерфейса; уже загруженные данные остаются доступными для просмотра.
- Автопереподключение `sessions/[id]/feed` (повторный long-poll/SSE после восстановления сети).
- Таймеры карточек продолжают идти локально — отсчёт от `startedAt` и полученных меток, без серверных тиков.
- Ввод в карточке буферизуется в localStorage и досылается после восстановления соединения.
- Сбой ≤ 30 сек — без потери данных и без сброса состояния экрана.

## Имитация ИИ-модулей

Все «ИИ»-ответы берутся из моков (готовые оценки, инсайты, реплики абонента). В коде — отдельный адаптер `AiGateway` с пометками `// ИИ-модуль: заменить на реальный сервис`. UI обязан честно показывать, что оценка/инсайт сгенерированы системой (бейдж «ИИ», см. `07-design-guidelines.md`), и давать преподавателю приоритет (ручная корректировка поверх оценки ИИ, Q&A в3).

## Сессия занятия (состояния)

`draft → configured → running → finished → reported`. Подробно — `06-user-flows.md` и `05-data-models.md` (`Session`).

## Производительность (из ТЗ §7 — для справки, в моках не гоняем нагрузку)

- отклик интерфейса ≤ 2 сек при 100 пользователях; ≥ 20 одновременных сессий;
- VoIP-задержка ≤ 150 мс (для реального контура; в тестовом фронте — эмуляция);
- восстановление сессии после сбоя сети до 30 сек без потери данных (буферизация ввода карточки в localStorage как демонстрация).
