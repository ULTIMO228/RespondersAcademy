# Фаза 0 — исследование и решения (фича 007)

Все неизвестности Technical Context закрыты ниже; маркеров `NEEDS CLARIFICATION` нет. Факты о коде — выводы исследования 2026-10-20 (`spec.md`, раздел «Исследование»), перепроверяются в задачах перед правкой каждого файла.

## D1. Где хранится специализация

- **Решение**: колонка `users.specializations` (JSON-список значений `"operator112" | "dds"`, как `assigned_groups`, `app/models/user.py`), у `teacher`/`admin` — `null`. Значения совпадают со словарём режимов проекта (`operator112 | dds`, конституция V, `TrainingMode`), новый словарь не вводится.
- **Почему**: поле нужно и фронту (меню, гварды), и бэкенду (проверки); `get_viewer` (`backend/app/api/deps.py:87`) уже читает строку `User` на каждый запрос, значит, специализацию можно положить в `Viewer` без второго запроса и без изменения формата токена.
- **Отклонено**: claim в JWT — после смены специализации старые токены врали бы до истечения; отдельная таблица связей — избыточно для двух значений (YAGNI, конституция IV); новая роль вместо специализации — ломает `Role`, RBAC, `proxy.ts` и матрицу `02-roles.md`.

## D2. Как фронт узнаёт специализацию

- **Решение**: поле `specializations?: Specialization[]` добавляется в `PublicUser` (ответ `GET /auth/session`, `/auth/login`, `/users`); серверные лэйауты берут его из `verifySession()` (`src/entities/user/index.server.ts`). `proxy.ts` остаётся оптимистичным по роли и специализацию не читает (он не проверяет подпись, и доверять ему специализацию нельзя).
- **Почему**: гварды уже серверные и получают пользователя целиком; JS-код в браузере токен не видит (инвариант AGENTS §3).

## D3. Что считается «зоной» и как защищаются зоны

- Зона 112: `/arm/operator112` и API `operator112/*`, действия попытки 112.
- Зона ДДС: `/arm`, `/arm/card/*`, `/arm/phone` и ДДС-часть compat API (попытки, статусы, звонки по карточке).
- **Решение**: единая серверная проверка `require_specialization(viewer, mode)` — `teacher`/`admin` пропускаются (режим просмотра), студент без нужной специализации → 403 «Недоступно для вашей специализации»; на фронте — `requireSpecialization(mode)` рядом с `requireSessionUser`, отказ → `/forbidden` (как чужая роль).
- Цепочка (`chain`) требует обе специализации (допущение 3 спеки).

## D4. Граница с анонимными эндпоинтами

- Исследование показало ряд записывающих эндпоинтов без авторизации. Проверка специализации применима только при наличии `viewer`.
- **Решение**: в этой фиче проверка включается на всех путях, где создаётся попытка или пишется от имени обучающегося (`operator112/*`, `assignments/{id}/start`, `cards/{id}/attempt`, события и отправка); остальные анонимные записи остаются и выносятся в отдельную фичу безопасности (предлагается 008). Без закрытия анонимности специализация на этих путях обходима — это записано в риски и в «Вне объёма» спеки.

## D5. Карточка ДДС: поля 112 только для чтения

- **Решение**: в `incident-card` ввести гранулярную блокировку (по блокам: адрес, телефоны, заявитель/флаги ЧС/ЧП, описание, «Дополнить», SMS, напоминания/«Важное»), включаемую для обучающегося-ДДС; существующий `readOnly` (просмотр преподавателем) не трогаем. Статусы реагирования и данные своей службы остаются активными.
- **Почему**: сегодня `readOnly` — всё или ничего (`IncidentCardView.tsx:18,33`), а ДДС должен править только своё. Аутентичность АРМ (AGENTS §9): визуально блокировка выглядит как нормальное «только чтение» боевой карточки, лишних элементов не добавляется.

## D6. Доработка рабочего места 112 (разбивка по риску)

- **Обязательное (US2)**: «Сохранить» с подтверждением оповещения → «Зарегистрирована»; «Отработана»; «Закрыть карточку» из «Создана/Завершена/Отменена»; «Нет контакта», «Срыв звонка».
- **Второй эшелон**: перевод вызова (удержание, другому оператору) и привязка связей — фиксируются как событие в карточке и оценке, без реальной телефонии (софтфон — UI-эмуляция, AGENTS §10).
- **Вне плана**: Карта, Сводка, База знаний (допущение 5).
- **Источник правил**: памятка (стр. 14, 27) и единый документ §3.2–3.13; московская модель статусов, вендорская не используется (допущение 9).

## D7. Нормативы и отчёты

- Оценщики уже раздельны (`dds-1.1.0`, `operator112-1.0.0`). Работа: подписи «к какой роли относится норматив» в отчётах, успеваемости и карте ошибок; точки отсчёта 3 мин не менять (ДДС — от открытия, 112 — от ответа), только объяснить.
- Попытки 112 с пустым `session_id` (`operator112_service.py:188`) включить в отчёты: не создавая сессий, а выбирая попытки по `assignment_id` в `report_builder` — решение уточняется тестом на первом шаге задачи.

## D8. Назначение и цепочка

- Мастер назначений (`features/assignment-create`) фильтрует обучающихся по специализации режима; бэкенд `assignment_service.create` повторяет проверку (фронт — только удобство).
- Выдача карточки из 112 в журнал ДДС (`chain_service.issue_submitted_card`) ограничивается обучающимися со специализацией ДДС; срабатывание вне задания «цепочка» остаётся только в занятиях с явным `cardSource`.

## D10. Контракты и аутентичность

- Поле `specializations` — необязательное расширение (`[расширение]` в `types/user.ts`), старые клиенты не ломаются; после правки TS-типов — `scripts/extract_ts_fields.py`.
- `/arm/*` защищено снимками `e2e/simulator-visual.spec.ts` и тестом `simulatorBoundary.test.ts`: подпись зоны/переключатель добавляются в существующую панель «В кабинет» в токенах АРМ, а не в сам АРМ.

## D11. Сверка статусов рабочего места 112

- Текущие `IncidentCard`/`ArmCardFixture` и API оператора 112 используют учебную модель: отправка завершает попытку и создаёт карточку со статусом `registered` («Зарегистрирована»). Отдельного жизненного цикла статусов карточки 112 в этих моделях пока нет.
- Доменная памятка «Работа с АРМ-112 для ДДС от ОКр_ГСИ», стр. 27, задаёт `Зарегистрирована` (карточка сохранена), `Отработана` (специалист 112 завершил оповещение), `Завершена` (все службы завершили работу); `Отработана` не равна `Завершена`.
- `research/arm-112/docs/INTERFACE.md` §5.1 описывает отдельный вендорский жизненный цикл карточки у ДДС; его состояния (`Создана`, `Новая`, `Реагирование`, `Завершена`, `Отменена`, `Закрыта`) нельзя подменять статусами из памятки для режима 112.
- Для US2 поле `cardStatus` и события 112 должны хранить словарь памятки; статус службы/ДДС остаётся отдельной моделью. Имена `registered`, `processed` и `closed` — учебные коды новых событий, а не утверждение о наличии такого полного status-поля в текущей модели.
