# Исследование и решения: визуальный конструктор сценариев (фича 013)

Формат каждого пункта: **Решение** → **Почему** → **Отвергнутые варианты**. Факты о текущем коде — по результатам аудита 2026-10-19, ссылки на файлы даны.

## R1. Движок по правилам, ИИ не обязателен

- **Решение:** исполнение и оценка — детерминированная чистая функция `replay(граф, зерно, события, сейчас)`. ИИ-шлюз в конструкторе не используется. В будущем ИИ можно добавить как необязательного помощника автора (например, «предложить реплики»), с бейджем «ИИ», не влияющего на оценку.
- **Почему:** требование владельца; конституция, принципы II–III (каждая ошибка объяснима, итог раскладывается на детерминированные компоненты); воспроизводимость (SC-003).
- **Отвергнуто:** LLM-оценка ответа студента — недетерминированно, требует модели, противоречит запросу.

## R2. Где хранится схема: новые таблицы, а не поле в `scenarios.doc`

- **Решение:** отдельные `scenario_flows` и `scenario_flow_versions` (+ связь с заданиями), миграция `0006`.
- **Почему:** нужны неизменные версии с согласованием и привязкой заданий к точной версии. У `scenarios` есть только `doc` + `history`, неизменности на уровне БД нет (`backend/app/models/scenario.py`). Готовый образец — `ai_scenario_versions` + `assignment_scenario_versions` с триггерами неизменности (`backend/app/models/ai_scenario.py`, `backend/app/models/assignment.py`).
- **Отвергнуто:**
  - поле `flow` в `scenarios.doc` с компиляцией в `cardIds` + `expectedActions` (вариант аудита) — линейный эталон не выражает ветвления, условия и реплики; потеряли бы главное, что просит владелец;
  - переписать `scenarios` целиком — ломает фичи 000–003.

## R3. Где исполняется: через «Назначения», не через групповые занятия

- **Решение:** схема выдаётся существующими заданиями (`/api/v1/assignments`, `backend/app/services/assignment_service.py`), новая связь `assignment_flow_versions`. Студент работает в существующем симуляторе.
- **Почему:** задания уже поддерживают тренировку и экзамен, порог, срок, группы и точную версию сценария. Групповое занятие (`session_engine.py`) строит общую очередь карточек и ветвления по студенту не выдерживает без переделки.
- **Отвергнуто:** отдельный экран прохождения схемы — нарушил бы аутентичность АРМ-112 (`AGENTS.md` §9).

## R4. Движок пересчитывает состояние при чтении, без фоновых задач

- **Решение:** состояние прохождения не хранится пошагово, а вычисляется из журнала событий на каждый запрос (`GET /flow-runs/{id}`). Сроки — по серверным часам на момент запроса. Итоговый `trace` и балл сохраняются один раз при завершении.
- **Почему:** нет таймеров и очередей, переживает перезапуск сервера, тот же код — для теста и пересчёта.
- **Риск:** «Вводная с задержкой» и «Условие с ожиданием» появятся только при следующем опросе. Решение: фронт студента уже опрашивает ленту сообщений (`work-message-feed`); интервал 3–5 с достаточен для учебных задач.
- **Отвергнуто:** фоновый планировщик или вебсокеты — лишняя инфраструктура для прототипа (конституция, IV).

## R5. Без кругов в первой версии

- **Решение:** схема — граф без циклов (проверка E03, правило соединения С5).
- **Почему:** гарантированное завершение, конечное число путей (можно посчитать максимум баллов и проверить каждый путь), простое объяснение. «Повтор вопроса» выражается веткой «Неверно → реплика → дальше».
- **Отвергнуто:** циклы с лимитом повторов — нужно для v2, если преподаватели попросят «повторять, пока не ответит».

## R6. Холст: своя реализация на SVG и HTML без новых зависимостей

- **Решение:**
  - блоки — абсолютно позиционированные HTML-элементы (доступность, крупный текст, токены `--pf-*`);
  - стрелки — SVG-кривые Безье с подписями выходов (как в Unreal Blueprints);
  - панорамирование и масштаб — CSS `transform`;
  - перетаскивание — Pointer Events;
  - клавиатурная альтернатива — выбор «Следующий шаг» в свойствах.
- **Почему:**
  - в `package.json` сейчас только `next`, `react`, `react-dom`, графовых библиотек нет;
  - правило проекта: новые зависимости только по необходимости (`AGENTS.md` §7);
  - объём холста первой версии (до 150 блоков, без вложенности) укладывается примерно в 1–1,5 тыс. строк;
  - полный контроль над внешним видом «в том же дизайне».
- **Отвергнуто:** `@xyflow/react` (React Flow, MIT) — экономит время на холсте, но это новая зависимость. Её совместимость с установленными React 19.3 / Next 16.3.5 не проверялась (в контейнере аудита нет `node_modules`), и кастомизация под токены платформы всё равно нужна. Остаётся запасным вариантом: если к концу фазы 3 холст не готов, вынести решение владельцу и записать в `docs/LIBRARIES.md`.

## R7. Входы и выходы без типов данных

- **Решение:** по стрелкам передаётся только ход; сведения о студенте движок держит в журнале, блоки читают их по выбору из справочника.
- **Почему:** требование «не заставлять разбираться в переменных и типах»; меньше способов собрать ошибочную схему.
- **Отвергнуто:** провода данных как в Unreal (булевы, строки) — мощнее, но требует понимания типов.

## R8. Роли без изменения авторизации

- **Решение:** «эксперт» — любой преподаватель, кроме автора; «руководитель группы» — преподаватель с группой в `assignedGroups`. Роли остаются `student | teacher | admin` (`backend/app/api/deps.py:24`, `src/shared/api/types/user.ts:5`).
- **Почему:** решение владельца 2026-10-19; ноль правок JWT, `proxy.ts`, `verifySession`, навигации ролей.
- **Отвергнуто:**
  - новые роли `expert` / `groupLead` — правки авторизации, гвардов, сидов, админки, контрактов, тестов RBAC;
  - флаг «эксперт» у преподавателя — оставлен открытым вопросом В1.

## R9. Конструктор только с бэкендом

- **Решение:** API под `/api/v1/flows*` и `/api/v1/flow-runs*`. Мок-обработчиков во фронте нет; без бэкенда раздел показывает «требуется сервер» (готовый механизм T007 фичи 002).
- **Почему:** одна реализация проверки и движка (Python) вместо двух (TS + Python) — снимает риск расхождения. Задания v1, через которые схема исполняется, тоже работают только с бэкендом.
- **Отвергнуто:** зеркальная реализация в мок-слое `app/api/mock` — двойная работа и двойной объём тестов.

## R10. Справочники для настроек блоков — с сервера одной точкой

- **Решение:** `GET /api/v1/flow-blocks` отдаёт каталог блоков (подписи, выходы, настройки, допустимые значения из `reference`, `classifier`, `cards`). Библиотека и инспектор строятся по нему.
- **Почему:** подписи и правила в одном месте; сервер проверяет ровно то, что предлагает интерфейс.

## R11. Связь с картой ошибок и отчётами

- **Решение:**
  - оценка по каждой карточке пишется в существующие `evaluations` (`assessor_version = "flow/1"`);
  - ошибки — в формате `EvaluationError` + необязательные поля (`ruleId`, `stage`, `nodeId`, `expected`, `actual`, `pointsLost`);
  - карта ошибок принимает явный `stage`, если правило не из раскладки.
- **Почему:** отчёты, журнал группы, правка оценки и карта ошибок работают без переделки (SC-006).
- **Риск:** `tests/contract/expected_fields.json` нужно обновить после правки TS-типов (`scripts/extract_ts_fields.py`).

## R12. Расположение спек

- **Решение:** `spec/013-visual-scenario-builder/` (правило проекта `AGENTS.md` §8), а не `specs/` (умолчание speckit). `.specify/feature.json` указывает сюда.
