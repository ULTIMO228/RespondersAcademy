# Research: поэтапное сведение веток (021)

Факты собраны 2026-10-20 read-only командами git (`fetch --unshallow`, `log`, `merge-base`,
`patch-id`, `merge-tree --write-tree`, `ls-tree`, `show`). Сборка и тесты веток не запускались.

## R1. Способ переноса: merge с историей, а не rebase и не squash

- **Decision**: каждый кусок вливается `git merge --no-ff` в интеграционную ветку. Частичное взятие —
  только `cherry-pick -x` с записью в журнале.
- **Rationale**: FR-006 требует сохранить авторство. У веток есть живые авторы, и rebase сломал бы им
  дальнейшие слияния. Merge-коммит на кусок даёт откат одним `git revert -m 1` (FR-009).
- **Alternatives**: rebase всего на main (переписывает чужие хеши и ломает ветки авторов);
  squash по куску (теряет авторство, повторяет проблему `98705b7`); octopus merge (нельзя проверить по кускам).

## R3. Миграции БД — merge-ревизии, без перешивки цепочек

- Факт: id ревизий уникальны (`0006_ai_settings`, `0006_user_training_profile`, `0006_scenario_builder`…).
  Повторяются только числовые префиксы имён файлов. Все три цепочки отходят от `0005_error_map_verdicts`.
- **Decision**: после слияния каждой второй и последующей цепочки добавить пустую merge-ревизию
  (`alembic merge`) с двумя родителями. Существующие ревизии и файлы не переименовывать.
- **Rationale**: БД, созданные на любой исходной ветке, обновляются `upgrade head` без ручных правок:
  применяются только недостающие ветви (US5, сценарий 2). Тест `test_alembic.py` (`upgrade head`)
  требует одной головы, и merge-ревизия её даёт.
- **Alternatives**: перешить `down_revision` в линию 0006…0016. Это ломает уже созданные БД: alembic
  считает пропущенные ветви применёнными, таблиц нет.
- ⚠️ Две цепочки добавляют колонки в `users`: `training_profile` (K2), `specializations` (K7),
  `permissions` (K11). Технически они совместимы, но специализация по смыслу дублируется (R5).

## R5. Модель специализации обучающегося (решение владельца, до F5)

- K2 (`training_profile`, String(16)): одна специализация на учётную запись, ivanov — «чистый» 112.
- K7 (`specializations`, JSON-список): у пользователя может быть одна или обе. В моках u-005, u-006 —

  мигрировать в список, код K2 перевести на него. Окончательное решение — за владельцем, вопрос **В1**.

  Тесты бэкенда `test_ai_chain` и `test_seed_chain_demo` переносятся или удаляются только после
  проверки, что их сценарий покрыт другим тестом.

## R7. Слот simulator-bar: Portal (K3) против Slot (K4)

- K3: `SimulatorBarPortal` + `SIMULATOR_BAR_SLOT_ID`, используется в `Operator112Session.tsx`.
- K4: `SimulatorBarSlot` + `data-simulator-bar-slot`, используется в `TrainerNorms.tsx`.

  Владельцу не выносится: это внутреннее устройство, видимый результат не меняется.
