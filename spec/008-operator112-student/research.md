# Research: 008 — учётка ivanov как чистый специалист-112

Дата: 2026-10-20. Источник фактов — текущий код ветки `007-arm-one-to-one` (после merge `origin/main`, 5f4988e).

## Что есть сейчас (установлено по коду)

- `User` (`backend/app/models/user.py`): `group`, `service`, `assigned_groups`; признака «режим обучаемого» нет. ivanov (`u-005`) — `group: ДДС-01`, `service: ДДС района Чертаново Южное` (`spec/000-фронт/mocks/users.json`, копия в `mocks/users.json`).
- `service` уже используется как **профиль службы ДДС**: `session_engine.resolve_student_profile` + `PROFILE_MAPPING_SEED` сужают билеты ДДС по службе; для `operator112` профиль не применяется (`filter_cards_for_student`, `training_mode != "operator112"`).
- Назначение (`assignment_service.create`) принимает явный `studentIds`; группа раскрывается во фронте (`features/assignment-create`, шаг «Обучающиеся» идёт **до** шага «Режим и формат»).
- Курсант видит свои задания через `list_rows` / `detail` / `start` — фильтр только по `student_ids`, без режима.
- Занятия (`session_engine.create_session`) принимают `trainingMode` ∈ {dds, operator112}; состав курсантов проверяется только на роль.
- Рекомендации (`recommendation_service.generate`) строятся по истории обоих режимов и могут предложить «Повторить режим dds» (R10, `modeGap`).
- Изменения пользователя админом пишутся в аудит строками вида «служба «…» → «…»» (`api/compat/admin_users.py::_changes`).
- Миграции — Alembic, последняя `0005_error_map_verdicts`.
- Сверка полей TS ↔ Python — `backend/tests/contract/expected_fields.json`, генерируется `backend/scripts/extract_ts_fields.py`.

## Решения

### R1. Где хранить профиль режима

- **Decision**: новое необязательное поле пользователя `trainingProfile` (`training_profile` в БД) со значениями `"operator112" | "dds"`; отсутствие = «не задан». Колонка nullable, миграция `0006_user_training_profile`.
- **Rationale**: значения совпадают с `TrainingMode` назначений — сравнение без таблиц соответствия; nullable сохраняет поведение 19 остальных курсантов (SC-005); тот же механизм нужен будущей учётке ДДС (FR-005).
- **Alternatives**: выводить режим из `service` (строка «ДДС района …») — хрупко, `service` уже несёт профиль службы ДДС; через `group` — группа учебная, в ней смешанные курсанты; отдельная роль `operator112` — ломает ролевую модель student/teacher/admin и все проверки `role == "student"`.

### R2. Подпись службы для ivanov

- **Decision**: `service: "ЦОВ системы-112"`.
- **Rationale**: в материалах проекта рабочее место специалиста-112 — ЦОВ (центр обработки вызовов), экран — ПОВ-112; профиль службы ДДС к режиму 112 не применяется, так что смена `service` ничего не сужает. Для чистоты: профиль службы ДДС для курсанта с `trainingProfile = operator112` не вычисляется вовсе.
- **Alternatives**: оставить «ДДС района Чертаново Южное» — противоречит US1-2; пустое поле — в шапке/кабинете появится «—».

### R3. Одна точка правила

- **Decision**: модуль `backend/app/services/training_profile.py`: `allows(user, mode) -> bool`, `blocked_message(mode)`, `split_by_profile(users, mode) -> (allowed, blocked)`. Вызовы:
  1. `assignment_service.create` — если среди `studentIds` есть заблокированные → 400 «Задание режима ДДС нельзя назначить: профиль специалиста-112 — Иванов С. П.» (FR-004, обход мастера).
  2. `assignment_service.list_rows` (viewer — student) — скрыть задания чужого режима; `detail`/`start` для курсанта → 403 с `blocked_message` (FR-003, прямая ссылка).
  3. `session_engine.create_session` — 400 при заблокированных курсантах; список занятий курсанта и вход в занятие — фильтр/403.
  4. `recommendation_service.generate` — история и предложения только разрешённого режима; без R10 «Повторить режим …» к запрещённому режиму.
  5. Кабинет курсанта (`lobby` history/analytics) — строки только разрешённого режима.
- **Rationale**: правило проверяемо одним набором юнит-тестов; сервер — источник истины, фронт только подсказывает.
- **Alternatives**: проверки только во фронте — обходится прямым запросом (US2-3); декоратор на роутерах — режим известен только после загрузки задания.

### R4. Мастер назначения: шаг «Обучающиеся» идёт до выбора режима

- **Decision**: на шаге «Обучающиеся» у курсанта с профилем — метка «112» / «ДДС» (`Tag`). На шаге «Режим и формат» при выборе режима, несовместимого с частью выбранных, — `Alert` «Пропущены (профиль специалиста-112): Иванов С. П.»; такие курсанты исключаются из `studentIds` при создании и не показываются в составе на шаге «Проверка». Если исключены все — ошибка шага «Нет обучающихся для режима ДДС».
- **Rationale**: порядок шагов не меняется (тесты мастера, `initialFromQuery`); поимённый и групповой выбор обрабатываются одинаково; требование «недоступен с пояснением» выполняется на шаге, где режим уже известен.
- **Alternatives**: переставить шаги (режим первым) — правка всех тестов мастера и deep-link `initialFromQuery`; молча убирать — нарушает US2-2 (преподаватель должен видеть, кто пропущен).
- **Спека**: формулировка US2-1 уточнена под этот порядок шагов.

### R5. Ошибки: код и текст

- **Decision**: создание назначения/занятия с несовместимым курсантом — `400 validation_failed`; открытие/запуск курсантом — `403 forbidden`. Текст: «Задание режима ДДС недоступно для учётной записи специалиста-112» (зеркально для ДДС).
- **Rationale**: совпадает с существующими «Обучающемуся доступны только свои задания» (403) и «Все studentIds должны…» (400); фронт уже показывает `message` из этих ответов.

### R6. Существующие базы и демо-данные

- **Decision**: сиды (`spec/000-фронт/mocks/users.json` и копия `mocks/users.json` через `npm run mocks:sync`) получают `trainingProfile: "operator112"` и новую `service` у `u-005`; `seed/load.py` переносит поле. Миграция `0006` добавляет колонку и data-шагом проставляет ivanov профиль и службу (`WHERE login = 'ivanov'`), чтобы `backend/var/demo.db` и dev-базы не требовали `--reset`.
- **Rationale**: правило проекта «не сбрасывать базы без владельца» (SESSION_STATE, Caution); идемпотентно.
- **Alternatives**: только сид + `--reset` — теряются попытки и вердикты на стендах.
- Старые задания ДДС у ivanov не удаляются (FR-007); у преподавателя прогресс по ним остаётся.

### R7. Админка

- **Decision**: в `UserFormFields` для роли «Обучающийся» — select «Профиль режима: Не задан / Специалист системы-112 / Диспетчер ДДС». Бэкенд `admin_users` принимает `trainingProfile` (`null` = сброс), для не-студентов поле обнуляется (как `group`); `_changes` добавляет «профиль «…» → «…»». Мок-слой `app/api/mock/admin/users` — то же поле.
- **Rationale**: в одном стиле с `group`/`service`; аудит без новых типов событий.

### R8. Что не трогаем

- Экраны АРМ (spec/007 FR-001): ни меток профиля, ни пояснений. Профиль виден только в кабинете/админке/мастере.
- Задания `chain` — только просмотр, как сейчас.
- Учётка диспетчера ДДС не создаётся (решение владельца 20.10.2026).
