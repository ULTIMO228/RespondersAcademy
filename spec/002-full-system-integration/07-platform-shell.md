# Платформа-обложка: обучающая система вокруг симулятора АРМ-112 (Фича 002, часть B)

**Статус**: проект, согласован с владельцем в чате 2026-09-29 (формулировка: «обложка с похожим по дизайну, но более красивым фронтом, все необходимые страницы: аналитика, мой кабинет, справочник и т.п.; правильная авторизация»). Интерпретация границ — допущение A11, подтверждает владелец.
**Связь**: расширяет `spec.md` (US6–US9, FR-050…FR-089), `plan.md` (разделы «Платформа» и фазы 2–3, 7–8), `research.md` (R14–R19), `tasks.md` (T032…).

## 1. Проблема

Фронт проекта — это эмулятор АРМ-112 «1:1» (решение владельца 2026-09-18, `spec/000-фронт/07-design-guidelines.md`, правило №1). Для экспертов и для замысла ТЗ этого мало: продукт — **обучающая система для специалистов**, а не копия рабочего места. Проверено в приложении (2026-09-29):

| Что видно | Доказательство | Почему проблема |
|---|---|---|
| После входа обучающийся сразу попадает в тёмный журнал АРМ (`/arm`) | Скриншот `/arm`; `ROUTES.arm` — цель редиректа по роли | Нет «дома» обучающегося: нет заданий, ближайших дедлайнов, прогресса, рекомендаций |
| «Прогресс» и «Справка» оформлены как таблицы боевой системы, шапка та же, что у симулятора | Скриншоты `/arm/progress`, `/arm/help` | Учебные страницы неотличимы от рабочего инструмента; плотные графитовые таблицы вместо аналитики |
| У преподавателя и администратора те же графитовые вкладки, нет экрана создания заданий | `NAV_ITEMS`; в `src/` нет клиента `assignments` | Ключевой учебный процесс (назначение) недоступен из интерфейса |
| Нет профиля, смены пароля, справочника, истории с разбором попыток | Нет страниц/клиентов | Нет «моего кабинета» |
| Вход — копия экрана «112 ВХОД В СИСТЕМУ» с полем «Номер АРМ» у всех ролей, демо-панель учёток | Скриншот `/login`; `AuthForm`; бэкенд `_read_arm_number` (`compat/auth.py:34-41`) | Артефакт симулятора протекает в платформу |

### 1.1. Авторизация: что не так на самом деле (факты)

1. **Сессия — читаемый и подделываемый cookie.** `arm112_session` пишется **клиентом** (`src/entities/user/model/session-store.ts:61`), не `HttpOnly`, содержит JSON `{ userId, role, token, twoFactorUsed, issuedAt }` (`session.ts:52-62`); JWT виден скриптам страницы (кража при XSS). `proxy.ts` и серверные лэйауты доверяют этому JSON **без проверки подписи**: любой может выставить `role: "admin"` и пройти гвард страницы. API с бэкендом защищён JWT, но оболочка и мок-режим — нет.
2. **Проверка жизни сессии — только по времени 24 ч в самом cookie** (`SESSION_TTL_MS`): отозвать сессию нельзя, серверный выход не влияет на копию cookie. (На бэкенде есть таблица `auth_sessions` и отзыв `revoke_user_sessions`, но UI не использует.)
3. **Логин требует «Номер АРМ»** для всех ролей (бэкенд: 422 «Укажите номер АРМ»); у преподавателя и администратора АРМ — фикция.
4. **2FA заявлена, но не работает**: спека входа требует шаг 2FA, бэкенд `GET /auth/policy` отдаёт `twoFactorRequired: false` и отвергает поле `twoFactorCode` (`compat/auth.py:56-57`) — расхождение спецификации и кода; в cookie всегда `twoFactorUsed: false`.
5. **Нет смены пароля самим пользователем.** Есть только `POST /admin/users/{id}/reset-password` → временный пароль (`admin_users.py:212-224`): выданный пароль остаётся навсегда.
6. **Нет управления сессиями** («выйти на всех устройствах»), нет простоя (idle timeout), не показан лимит попыток входа (бэкенд ведёт `auth_throttle`, `lockAfterAttempts` из политики).
7. **`document.cookie` читается кодом** (`src/pages/incident/lib/mockApiFetch.ts:66`) — после перевода cookie в `HttpOnly` этот вызов сломается и должен быть заменён.

Next.js 16.3.5 в своём руководстве по аутентификации (`node_modules/next/dist/docs/01-app/02-guides/authentication.md`) рекомендует: сессия в `HttpOnly`-cookie (стр. 631–649), в `proxy` — только **оптимистичная** проверка без обращения к БД (стр. 1017–1033), полная проверка — в слое доступа к данным `verifySession()` (стр. 1121–1165). Целевая модель ниже следует этому.

## 2. Концепция

**Два контура в одном приложении.**

| Контур | Что это | Внешний вид | Где живёт |
|---|---|---|---|
| **Платформа** («обложка») | Обучающая система: вход, главная, задания, результаты, аналитика, справочник, профиль; у преподавателя — назначения, обучающиеся, группы, отчёты; у администратора — пользователи, система, аудит, безопасность | **Новый визуальный язык**: родственный АРМ (те же фирменные акценты оранжевый/синий, графитовая шапка, те же статусные цвета), но светлые поверхности, карточки, воздух, современная типографика | `/login`, `/student/*`, `/teacher/*`, `/admin/*`, `/reference/*`, `/account/*` |
| **Симулятор** (АРМ-112) | Рабочее место 112/ДДС, софтфон, карточка, режим специалиста-112 | **1:1 с боевой системой** (правило №1 остаётся внутри симулятора) | `/arm/*` |

**Правило границы**: переход в симулятор всегда осознанный («Открыть АРМ», «Начать задание»); внутри симулятора тонкая панель тренажёра («← В кабинет», задание, таймер) в токенах АРМ; уход из симулятора не теряет открытую попытку. Платформа никогда не рисуется поверх симулятора и наоборот. Обучающийся, переходя на боевую систему, по-прежнему не замечает разницы — это касается экранов внутри `/arm/*`.

Так сохраняются требование Q&A в7 (эксперты сверяют поля с боевой системой) и решение владельца 2026-09-18 **для симулятора**, а требования ТЗ §15 («современный, доступный, удобный») и новая задача «обучающая система» закрываются платформой. Это **поправка к решению 2026-09-18** (AGENTS §8): вносится явной отметкой в `07-design-guidelines.md` и в AGENTS §9 (задача T057).

### 3.2. Навигация платформы

Левая боковая панель (сворачиваемая) + верхняя панель (хлебные крошки, поиск по справочнику, профиль, выход). Пункты:

- **Обучающийся**: Главная · Задания · Результаты · Аналитика · Справочник · [разделитель] · Открыть АРМ (симулятор) · Профиль.
- **Преподаватель**: Главная · Назначения · Занятия (мониторинг, мастер) · Сценарии · Обучающиеся · Отчёты · Справочник · Профиль.
- **Администратор**: Главная · Пользователи · Система · Аудит · Безопасность · Справочник · Профиль.

Роль в шапке; индикатор «Учебная система. Не является рабочей системой-112» — постоянная плашка внизу боковой панели (граница ТЗ §4).

## 5. Визуальный язык платформы

### 5.1. Принципы (предложение для согласования)

1. **Родство с АРМ**: те же фирменные акценты (оранжевый `#ec653b` — главное действие, синий `#157dbd` — навигация/выбор, красный — нарушение), графитовая шапка/боковая панель, тот же статусный цвет и цветокод служб. Обучающийся узнаёт «тот же продукт».
2. **Красивее и легче**: светлый фон страницы, белые карточки с радиусом 8 px и мягкой тенью, сетка 8 px, воздух вместо плотных таблиц; таблицы — «спокойные» (зебра, строка-наведение), плотный режим — только внутри симулятора.
3. **Данные — главное**: крупные KPI с табличными цифрами, линейные и столбчатые графики на существующих `shared/ui/charts` с линией норматива; каждый график имеет текстовую таблицу-дублёр.
4. **Сдержанная типографика**: локальный системный шрифт (`--font-ui`), шкала 13/14/16/20/28, межстрочный 1.4; никаких CDN и внешних шрифтов (принцип I).
5. **Состояния как часть дизайна**: loading — скелетоны, empty — пояснение и действие, error — причина и «повторить», отдельное состояние «требуется сервер».
6. **Доступность платформы — по WCAG 2.2 AA** (в симуляторе палитра неприкосновенна, в платформе — обязательный критерий): контраст текста 4,5:1, цель нажатия ≥ 24×24 px, видимый фокус, работа с клавиатуры, `aria`-метки, `prefers-reduced-motion`.
7. Десктоп-first ≥ 1920 px (AGENTS §7), корректная работа от 1280 px; мобильная адаптация не входит.

### 5.2. Реализация

- Токены платформы — новый файл `src/shared/ui/styles/tokens-platform.css` с префиксом `--pf-*`, подключаемый из `vars.css` (единственное место с hex, AGENTS §7). Значения предлагаются в задаче T037 на основе токенов АРМ (не выдумываются заново): поверхности, тени, радиусы, отступы, шкала шрифта, цвета KPI/графиков.
- Набор компонентов платформы — `src/shared/ui/platform/`: `PlatformShell` (боковая панель, верхняя панель, хлебные крошки), `PageHeader`, `Card`, `StatTile`, `DataTable` (поверх существующего `table`), `EmptyState`, `Skeleton`, `Tabs`, `Stepper` (мастер), `Field` (формы), `Alert`. Существующие `panel`, `chip`, `status-chip`, `ai-badge`, `charts`, `modal`, `select`, `toggle`, `connection-banner` переиспользуются; иконки — существующий набор `icons/` + недостающие простые SVG локально.
- Симулятор продолжает использовать прежние токены (`tokens-journal/card/softphone`), новые токены его не затрагивают (проверка: визуальная сверка `/arm/*` до/после).

## 6. Модель авторизации (целевая)

```mermaid
sequenceDiagram
    autonumber
    actor U as Пользователь
    participant L as /login (платформа)
    participant N as Next.js (proxy + DAL)
    participant B as Бэкенд /auth/*

    U->>L: Логин + пароль
    L->>N: POST /api/mock/auth/login (rewrite → бэкенд)
    N->>B: credentials
    B->>B: проверка, throttle, аудит
    B-->>N: 200 + Set-Cookie: arm112_session=JWT; HttpOnly; SameSite=Lax; Path=/ (+Secure при HTTPS)
    N-->>L: тело: PublicUser (без токена)
    L->>U: редирект по роли

    U->>N: GET /student (страница)
    N->>N: proxy: оптимистично — cookie есть, JWT не истёк, роль допустима
    N->>B: DAL verifySession(): GET /auth/session (cookie пробрасывается)
    B-->>N: PublicUser | 401
    N-->>U: страница | редирект /login?returnUrl=…

    U->>N: Выход
    N->>B: POST /auth/logout (отзыв jti)
    B-->>N: 204 + Set-Cookie: arm112_session=; Max-Age=0
```

### 6.1. Требования к модели

1. **Cookie сессии** `arm112_session` выдаётся **сервером**: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` при HTTPS, срок — `JWT_TTL_HOURS` (24 ч); значение — только подписанный JWT (без JSON и без данных пользователя). Клиентский код cookie не пишет и не читает.
2. **`proxy.ts` — оптимистичная проверка**: cookie есть, структура JWT валидна, `exp` не истёк, роль (из полезной нагрузки) допускается для маршрута. Подпись в proxy не проверяется (секрет остаётся у бэкенда). Дополнительно **не доверять** proxy: защита данных — на сервере.
3. **DAL `verifySession()`** (`src/entities/user/index.server.ts`, кэш на рендер): вызывает `GET /auth/session` бэкенда (в мок-режиме — проверку подписанного cookie); результат — единственный источник роли и профиля для серверных лэйаутов и страниц. Любая неудача → редирект на `/login?returnUrl=…&reason=…`.
4. **Мок-режим (без бэкенда)** повторяет то же поведение: обработчик логина ставит `HttpOnly`-cookie с **HMAC-подписью** (секрет — серверная переменная процесса, при отсутствии генерируется при старте; перезапуск сервера сбрасывает сессии так же, как сбрасывает in-memory стор), `GET /auth/session`, `POST /auth/logout` с отзывом, смена пароля в in-memory сторе.
5. **Вход по логину и паролю** без «Номера АРМ» (поле убирается с экрана платформы). Бэкенд делает `armNumber` необязательным (обратно совместимо: если передан — сверяется); номер АРМ хранится в профиле и показывается в симуляторе.
6. **Политика паролей и блокировки**: длина ≥ `minPasswordLength` (8), блокировка после `lockAfterAttempts` (5) неудачных попыток — бэкенд уже ведёт; фронт показывает нейтральные сообщения («Неверный логин или пароль», «Учётная запись заблокирована. Обратитесь к администратору», «Слишком много попыток. Повторите позже») без уточнения, что именно неверно.
7. **Смена пароля** (`POST /auth/password`: текущий, новый): проверка текущего, политика, аудит `auth.passwordChange`, отзыв всех **других** сессий пользователя. Новый эндпоинт бэкенда.
8. **«Выйти на всех устройствах»** (`POST /auth/logout-all`): отзыв всех сессий (`revoke_user_sessions` уже реализован). Новый эндпоинт.
9. **Выход отзывает сессию на сервере** (`revoke_session` уже вызывается) и очищает cookie ответом сервера; повторное использование старого cookie → 401.
10. **Истечение сессии**: сервер отвечает 401, клиент показывает «Сессия истекла» и возвращает на `/login`, после входа — на запрошенный URL (`returnUrl` проверяется на принадлежность своему сайту — защита от open redirect).
11. **Простой (idle timeout)**: не вводится (не требуется ТЗ; фиксируется в допущениях A13).
12. **2FA**: в этой фиче не реализуется. Форма входа не показывает шаг 2FA, пока политика `twoFactorRequired = false`; спека входа и `COMPLIANCE.md` исправляются честной формулировкой (расхождение с ТЗ §5 указывается, а не маскируется). Альтернатива — реальный TOTP — вынесена в отдельную фичу (A14).
13. **Аудит**: вход, выход, смена пароля, отзыв всех сессий записываются бэкендом (`audit.record`).
14. **Демо-учётки** на экране входа: показываются только при `NEXT_PUBLIC_DEMO_MODE=true`, не на странице входа платформы по умолчанию — вынесены в сворачиваемую панель «Демо-доступ» (для экспертов).

### 6.2. Изменения бэкенда (нужны, малые)

## 7. Перенос существующего фронта

1. **Лэйауты**: `RoleLayout`/`AppNav` (графитовая шапка с вкладками) заменяются `PlatformShell`; лэйауты симулятора `ArmJournalLayout`, `ArmCardLayout`, `LightArmLayout` сохраняются, к ним добавляется тонкая панель тренажёра «В кабинет».
2. **Страницы преподавателя и администратора** сначала переносятся в `PlatformShell` **без переписывания содержимого** (волна 1), затем переоформляются по одной (волна 2) — чтобы каждая волна была рабочей и проверяемой.
3. **`/arm/progress`, `/arm/help`**: содержимое (`src/pages/progress`, `src/pages/help`) разбирается: аналитика и справочник переписываются в платформенном виде, полезные данные и тесты сохраняются; старые маршруты — редирект.
4. **`src/pages/login`**, `features/auth-form`: платформенный экран входа; логика формы (`useAuthForm`, `redirect.ts` с `returnUrl`) переиспользуется, поле АРМ и 2FA убираются, `CityIllustration` — по решению владельца (декоративный элемент; в платформе допустим фирменный фон).
5. **Сессия на клиенте**: `session-store`, `serializeSession`, `parseSession` (JSON-cookie) удаляются или сводятся к чтению профиля из `GET /auth/session`; `useSessionExpiry` заменяется реакцией на 401; `mockApiFetch` перестаёт читать `document.cookie`.
6. **Данные**: страницы платформы, опирающиеся на `/api/v1/*`, в автономном режиме показывают «Раздел требует подключения к серверу» (A3). Демонстрационный запуск платформы — только с бэкенд-контуром (`BACKEND_URL`); это фиксируется в `quickstart.md` и `docs/`.

## 8. Волны поставки

Единая схема — `tasks.md` (волны W1–W4). Порядок определяет принцип IV конституции: сначала замкнутый цикл двух режимов, потом «всё остальное»; платформа — «остальное», поэтому идёт после цикла.

| Волна | Содержание | Ценность |
|---|---|---|
| **W1 — замкнутый цикл двух режимов** | Основа; режим 112; задания; цепочка A → B с сообщениями служб и голосовым докладом | Демонстрируется главный учебный сценарий на симуляторе (минимальный срез) |
| **W2 — платформа и авторизация** | Безопасная сессия; токены, компоненты и оболочка; вход; главная, результаты, аналитика, справочник, профиль обучающегося; teacher/admin — в оболочке без переписывания | Появляется «обучающая система» вокруг симулятора |
| **W3 — кабинеты ролей** | Назначения, обучающиеся, группы, справочник с правкой, экспорт; главная, аудит, безопасность администратора; переоформление существующих страниц | Учебный контур «назначил → отработал → проанализировал» из интерфейса |
| **W4 — приёмка сдачи** | Стенд одной командой, скринкаст ≤ 5 мин, документация, финальный дифф | Готовность к защите |

Гейт согласования визуального языка (T037) можно провести параллельно W1: он не блокирует и не блокируется кодом W1.

## 9. Риски

| Риск | Мера |
|---|---|
| **Объём**: платформа + авторизация + переоформление втрое больше исходной фичи; срок конституции исчерпан | Волны W1–W4; каждая — рабочий и демонстрируемый срез; W1 — минимальный срез; переоформление ролей — после переноса в оболочку |
| **Конфликт с решением 2026-09-18 и AGENTS §9** | Поправка вносится явно (T057); граница «внутри `/arm/*` — 1:1» остаётся; проверка визуальной неизменности симулятора |
| **HttpOnly-cookie ломает клиентский код и мок-слой** | Инвентаризация мест чтения cookie (T034), паритет мок-обработчиков (T035), тесты |
| **Платформа зависит от v1-эндпоинтов, которых нет в мок-слое** | A3: демо платформы — с бэкендом; либо решение владельца о расширении мок-слоя (существенно) |
| **Красота — субъективна** | Токены и макеты согласуются до массового переоформления (T037–T038), скриншоты до/после в `docs/` |
| **Регрессия тестов фронта** (1255 Vitest) | Замена лэйаутов и сессии сопровождается обновлением тестов; `npm run check` и `npm run test` после каждой фазы |
