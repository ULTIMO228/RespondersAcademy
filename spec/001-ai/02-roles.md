# Роли и доступ в фиче 001

Источник роли — проверенная серверная сессия, а не `teacherId` или `studentId` из тела запроса. Привязка преподавателя к занятию и обучающегося к попытке проверяется при каждом чтении и изменении.

| Действие | Обучающийся | Преподаватель своего занятия | Администратор | Ответственный за выпуск модели |
|---|---|---|---|---|
| Видеть утверждённый сценарий своего задания | Да | Да | Да | Нет необходимости |
| Создавать/править/утверждать сценарий и эталон | Нет | Да | При назначенных полномочиях | Нет |
| Сдавать карточку и видеть свою предварительную/итоговую оценку | Да, только свою | Просмотр своих групп | Административный просмотр по аудиту | Нет |
| Видеть полный разбор попытки и реестр группы | Только свои ошибки | Да | Да по служебной роли | Только обезличенный eval-набор |
| Разрешать спор, менять балл, добавлять ручную ошибку | Нет | Да, обязательны причина и аудит | По служебной роли с аудитом | Нет |
| Готовить выборку, обучать, принимать релиз модели | Нет | Может размечать/исправлять эталон | Нет без отдельного полномочия | Да, вне занятия, после gate очистки |

`Ответственный за выпуск модели` — операционная роль процесса подготовки, не новый аккаунт фронта и не обход RBAC. Активация релиза выполняется локальным администратором установки по подписанному/проверенному manifest; сырые билеты и данные студентов не доступны runtime LLM. Действия преподавателя и администратора логируются.

Студент не видит чужие ошибки даже через прямой ID endpoint. Преподаватель чужого занятия получает `403`/`404` согласно [контракту](contracts/ai-workflow-v1.md). Результаты группы доступны только преподавателю и уполномоченному администратору.
