# Быстрая проверка (Phase 1): Карта ошибок

Руководство для проверки готовой фичи. Детали форм и таблиц — в [contracts/error-map-endpoints.md](contracts/error-map-endpoints.md) и [data-model.md](data-model.md). Код ещё не написан: команды ниже верны после реализации по `tasks.md`.

## Подготовка

```bash
cd backend && uv sync --group dev
uv run python -m app.seed.load --reset      # после новой миграции 0005 и правки моделей
uv run alembic upgrade head                 # если БД ведётся Alembic
cd .. && npm ci
```

Стенд с реальным бэкендом (карта работает только с ним, решение D2):

```bash
./scripts/demo-up.sh                        # бэкенд :8000, фронт :3000 (или ./scripts/ai-up.sh); демо-набор карты ошибок подключается в demo-up (задача T019)
cd backend && uv run python scripts/seed_error_map_demo.py   # или отдельно, идемпотентно
```

Демо-вход преподавателя и обучающегося — как в `docs/demo-script.md` (логин/пароль из сидов; значения не копировать в чаты).

### Демо-набор карты ошибок (T019)

`backend/scripts/seed_error_map_demo.py` — детерминированные синтетические данные (фиксированные id, обезличенные имена):
8 групп (по четыре на режим), 36 обучающихся (логины `demo-dds-N-NN` и `demo-112-N-NN`, пароль — как у учебных
обучающихся, значение в скрипте), 8 занятий и 132 оценённые попытки с `Evaluation.errors`; `ruleId` — реальные правила
`ml/assess/rules.py`. Все оценки — за 1–12 дней до сегодня, то есть внутри окна 2w; числа одинаковы для любого периода.
Группы закреплены в `assignedGroups`: `ДДС-Демо-1…4` за морозовой (`morozova`), `112-Демо-1…4` за Ковалёвым (`kovalev`);
уже закреплённые группы сохраняются. Повторный запуск не дублирует строки. Запускать после `app.seed.load`, в том числе
после одного лишь обновления сида, потому что сид перезаписывает `assignedGroups`.

| Группа | Режим | Сценарий | Что видно на карте |
|---|---|---|---|
| `ДДС-Демо-1` / `112-Демо-1` | dds / operator112 | нет этапов «часто» | вывод «Критичных проблем нет» |
| `ДДС-Демо-2` / `112-Демо-2` | dds / operator112 | ровно два «часто» | «Тип происшествия» и «Статусы» (112: «Суть» и «Тип по классификатору») |
| `ДДС-Демо-3` / `112-Демо-3` | dds / operator112 | пять «часто» | в выводе три самых частых этапа |
| `ДДС-Демо-4` / `112-Демо-4` | dds / operator112 | 4 попытки при minAttemptsGroup 5 | все плитки серые, «мало данных» |

Обучающийся с индексом 4 в группе 2 (`demo-dds-2-05`, `demo-112-2-05`) хуже группы на «Тип происшествия» (112: «Суть
происшествия») и лучше на «Статусах» (112: «Тип по классификатору»). Обучающийся с индексом 5 в группе 3 сделал
две попытки: «мало данных», сравнения нет.

## Проверка удобства (SC-001 … SC-003)

1. Привлечь не менее 3 преподавателей (или сотрудников не из команды) в возрасте 40–50 лет; демо-данные те же.
2. Без подсказки попросить: «Назовите самый проблемный этап группы» (замер до 5 с), затем «Назначьте тренировку по нему» (замер ≤ 1 мин, ≤ 3 клика).
3. Записать клики, время и непонятные слова; правки формулировок вносить в тексты, не в логику.
4. Проверить расстояние чтения режима показа: монитор 24″, 3 м (SC-006).

Если людей нет, это ограничение надо назвать в `docs/FINAL-GATE.md`, а SC-001…SC-003 считать непроверенными, а не пройденными.

## Результаты проверок (2026-10-19)

- **Производительность (SC-004, T069)**: демо-набор (`seed_error_map_demo.py`), локальный бэкенд на SQLite, `curl` с cookie преподавателя, группа «ДДС-Демо-3»: карта группы — 34 мс на первом запросе, затем ~2,5 мс; разбор этапа ~3 мс; журнал за всё время ~3 мс. Объём демо-данных мал (132 попытки), на боевом объёме замер не делался; индекс не добавлялся.
- **HTTP-сценарий (T068)**: `bash backend/scripts/run_frontend_e2e.sh --only error-map` — 20 шагов из 20 пройдены (карта, разбор, журнал, PDF, вердикт, `/me/focus`, 403 и 401).
- **Не выполнено**: проверка удобства на людях (T072), ручные сценарии 1–14 в браузере (T073), `e2e/simulator-visual.spec.ts` (T067; правки в файлах симулятора отсутствуют, `simulatorBoundary.test.ts` проходит, браузерный снимок не запускался).
