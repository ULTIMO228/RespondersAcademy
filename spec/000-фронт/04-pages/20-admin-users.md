# 04-pages/20. Администратор: пользователи (`/admin/users`)

**Роль:** Администратор. **Основание:** ТЗ §8 (управление пользователями), Q&A в14 (3 роли).

## Состав

- **Таблица пользователей**: ФИО, логин, роль (бейдж), № АРМ, группа (для обучающихся), служба, состояние («активна»/«заблокирована» — поле `User.isActive`, `false` = заблокирована), создана. Фильтры: роль, состояние, группа; поиск по ФИО/логину.
- **Создание учётной записи** (форма/модалка): ФИО, логин, временный пароль, роль (3 фиксированных значения), № АРМ — для всех ролей (в реальном АРМ-112 вход выполняется с номером АРМ), для обучающегося — дополнительно группа, для преподавателя — закреплённые группы. Валидация уникальности логина.
- **Действия в строке**: редактировать, назначить/сменить роль (с записью в аудит), сбросить пароль, заблокировать/разблокировать (переключение `User.isActive`).
- **Права доступа**: справочная плашка-матрица «что может роль» (из `02-roles.md`) — read-only.

## Ограничения (ТЗ §8 — показывать в UI)

- Администратор не имеет доступа к оценкам и сценариям (ссылки на преподавательские разделы отсутствуют; прямой URL → 403).
- Доступ к персональным данным — по принципу минимальных привилегий: в таблице нет лишних персональных полей.

## Критерии приёмки

- CRUD пользователей на моках: созданный пользователь может войти; заблокированный (`isActive = false`) — получает отказ на `/login`.
- Смена роли и блокировка пишутся в аудит (`AuditLogEntry`).
