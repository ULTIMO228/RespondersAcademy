# 11. План реализации тестового фронта (implementation plan)

План построения тестовой системы по спецификациям `spec/00–10` и мокам `spec/000-фронт/mocks/`.
Результат этапа: работающий фронтенд Next.js + TS на мок-данных, проходящий демо-путь (`06-user-flows.md`) и чек-листы приёмки страниц (`04-pages/*`).

## 1. Технический контекст и решения

| Решение | Выбор | Основание |
|---|---|---|
| Фреймворк | Next.js (App Router) + TypeScript strict | `03-architecture.md` |
| Организация кода | FSD-слои в `src/` (app/pages/widgets/features/entities/shared), тонкие роуты в `app/` | `10-code-rules.md`, ПРАВИЛА-КОДА-ФРОНТ |
| Стили | CSS-модули + дизайн-токены в `shared/ui/styles/vars.css` | `07-design-guidelines.md`, `10-code-rules.md` §5 |
| Данные | Мок-слой: Route Handlers `app/api/mock/*` читают JSON из `spec/000-фронт/mocks/` (копия в `mocks/` приложения); клиент ходит только через `shared/api` | `03-architecture.md` |
| Реальное время | SSE/long-poll `sessions/[id]/feed` шаг 2–5 сек; таймеры клиентские от `issuedAt`/`startedAt` | `03-architecture.md` |
| Графики отчётов | Простые SVG-чарты собственными силами (bar/line/heatmap-таблица) — без внешних библиотек, чтобы не тащить зависимости в локальный контур | ТЗ §17 «объективность диаграмм», локальный контур |
| Линт/формат | ESLint (@typescript-eslint/recommended + react-hooks), Steiger (FSD), Prettier; Steiger = обязательный гейт CI | `10-code-rules.md` §4 |
| Тесты | Vitest/RTL — юнит для `entities`/`features`-логики (нормативы, граф статусов) + e2e-smoke демо-пути (Playwright) | testing-политика, `10-code-rules.md` §6 |
| Локаль | ru-RU; шрифт — локальный системный стек (без CDN); все ассеты локальные | ТЗ §8, Q&A в11 |

**Допущения (открытые вопросы из `spec/000-фронт/README.md`, принятые для плана):**
1. Софтфон — полная эмуляция с текстовым логом диалога (без аудио; аудио — этап 2).
2. Админка — полный набор экранов по ТЗ (`20/21`).
3. Мобильная адаптация — этап 2 (опциональна по ТЗ §6); планшеты — десктопная версия (ТЗ §15).
4. ИИ — имитация моками с бейджем «ИИ»; адаптер `AiGateway` в `shared/api` для будущей замены.

## 2. Гейты (конституция проекта)

Любая фаза считается завершённой только если:
- Steiger + ESLint + Prettier зелёные; нет `any`, магических чисел, транслита (`10-code-rules.md`).
- Соответствие спеке страницы: критерии приёмки `04-pages/*` выполнены.
- Аутентичность АРМ-112: компоновка/поля/термины — по `07-design-guidelines.md` (HARD-правило) и скриншотам-референсам.
- Данные — только из моков через `shared/api`; прямой fetch в компонентах запрещён.
- Валидация моков зелёная: `python3 spec/000-фронт/mocks/_tools/validate_mocks.py` → PASS.
- Юнит-тесты зелёные; демо-путь проходим вручную.

## 3. Структура репозитория приложения (целевая)

```
app/                            # только тонкие роуты-обёртки (App Router)
  login/page.tsx → @/pages/login
  arm/page.tsx · arm/card/[cardId]/ · arm/phone/ · arm/progress/ · arm/help/
  teacher/... · admin/...        # аналогично
  api/mock/.../route.ts          # мок-слой (route handlers)
src/
  app/        # провайдеры, глобальные стили, store сессии
  pages/      # login, journal, incident, phone, progress, help, teacher-*, admin-*
  widgets/    # incident-list, incident-card, service-panel, monitor-grid, report-charts
  features/   # status-form, call-control, incident-type-picker, statement-form,
              # scenario-builder, session-wizard, report-export, auth-form
  entities/   # incident, service, user, session, report, scenario
  shared/     # ui (timer-badge, status-chip, hotkey-hint…), api (мок-клиент + AiGateway),
              # lib (таймеры, форматтеры времени, буфер localStorage), config, styles/vars.css
mocks/        # копия spec/000-фронт/mocks (скрипт синка)
```

## 4. Фазы реализации

### Фаза 0 — Скелет и нормы (0.5 дня)
- `create-next-app` (TS strict), ESLint/Prettier/Steiger, алиасы `@/`, `vars.css` с токенами из `07-design-guidelines.md` (две темы, статусная палитра, цветокод служб).
- Скрипт `npm run mocks:sync` (копия `spec/000-фронт/mocks` → `mocks/`) + прогон валидатора в prebuild.
- Скелет роутов (пустые страницы с заголовком) + гварды ролей (заглушки редиректов на `/login`).
- **Проверка:** сборка зелёная, Steiger зелёный, все роуты отдают заглушки.

### Фаза 1 — Мок-слой и entities (1 день)
- `shared/api`: типы из `05-data-models.md` (User, IncidentCard, ArmCardFixture, Scenario, Session/CardEvent, Report, ReferenceData, ClassifierEntry); функции-ридеры JSON; эндпоинты по таблице `03-architecture.md` (включая links/worklines/reminders/sms/recordings/evaluation).
- Логика мок-слоя: фильтры карточек (расширенный поиск), граф переходов статусов из `reference.json (ddsStatuses/serviceStatuses)`, генерация feed занятия из `cardFlow`, вычисление `primaryReactionMs`/`fullProcessingMs`, мок-оценка (чтение `evaluation` из sessions.json / генерация по `Etalon` для новых попыток).
- Юнит-тесты: граф статусов (невалидный переход отклоняется), тайминги, фильтры поиска, `classifierName`-маппинг служб.
- **Проверка:** все endpoints отдают корректные данные; тесты зелёные.

### Фаза 2 — Auth + каркас АРМ (1 день)
- `00-auth.md`: форма логин+пароль+№ АРМ, 2FA-заглушка (дефолт вкл), блокировка `isActive=false`, автовыход 24 ч, редиректы по ролям.
- `01-arm-main.md`: тёмная тема; верхняя панель (дата/время живые, пользователь, автообновление, «выберите что показать»); таблица списка (колонки по референсу, раскрытие строки, таймеры 30 сек в строках новых карточек); расширенный поиск (все поля + множественность); пагинация; связи/будильник/молния-«важное»; «Мои назначенные модули».
- **Проверка:** критерии приёмки 00/01; вручную: вход тремя ролями, истечение таймера 30 сек красит строку.

### Фаза 3 — Карточка происшествия (1.5 дня) — ядро
- `02-arm-card.md`: светлая карточка по фикстуре `arm-cards.json`; верхняя телефония (4 статуса линии + авто-«недоступен» +10 сек); таймер 3:00 с красной шапкой при превышении; блоки заявитель/адрес/«Что случилось»/описание/журнал; «Действие диспетчера» (ручной ввод + буферизация localStorage); нижняя тёмная панель служб (плитки, двойное подчёркивание основных, попап истории); форма смены статуса (последовательность, обязательный комментарий, «Номер наряда»); дополнение/связи/отработки/записи разговоров/SMS; горячие клавиши (общие + режим просмотра); состояние «потеря соединения».
- `03-arm-softphone.md`: набор 3–4-значного номера, эмуляция вызова B→C (лог реплик ИИ из мока), журнал вызовов, запись в `cardEvents.calls`.
- **Проверка:** полный цикл статусов на карточке; попытка пишется в мок; красная шапка; горячие клавиши работают.

### Фаза 4 — Преподаватель (1.5 дня)
- `11-teacher-scenarios.md`: список/фильтры, редактор (параметры, эталон, предпросмотр, коррекция, утверждение частичное/полное), «Сгенерировать (ИИ)»-мок, профильные категории (привязка service→группы ЕКП), загрузка материалов-заглушек, проверка грамматики-мок.
- `12-teacher-session.md`: мастер занятия (группа, категории, cardSource 3-режима, сценарии approved, режим demo/follow/practice, тайминги, темп выдачи), старт/стоп в любой момент.
- `10-teacher-dashboard.md`: плитки курсантов с живыми таймерами (SSE), лента событий, экран курсанта `/teacher/monitor/[studentId]` (read-only зеркало `CardEvent`).
- `13-teacher-reports.md`: журнал отчётов; отчёт занятия (сводка, детализация попыток, grammarErrors spelling/syntax, ошибки по severity, ИИ vs преподаватель с аудитом, инсайты группы, чарты byStage/byErrorType/dynamics, экспорт CSV/PDF, индикация «сформирован за N сек»).
- **Проверка:** сценарии Б/В ТЗ §10 проходимы端到端; правка оценки пишется в аудит.

### Фаза 5 — Администратор + прогресс/справка (1 день)
- `20-admin-users.md`: CRUD пользователей (все поля включая № АРМ), блокировка `isActive`, аудит-записи.
- `21-admin-system.md`: сервисы (старт/стоп мок), мониторинг нагрузки (мок-графики против нормативов), настройки (телефония/БД/безопасность/бэкап ≥1/сутки с валидацией + сжатие/логи ≥6 мес), «Производительность», «Статистика использования», «Целостность», «Оповещения об ошибках» + автовосстановление, журнал аудита (события карточек включая «Нарушения исправлены»), блокировки во время активного занятия.
- `04-arm-progress.md`: сводка, история попыток с расшифровкой, «Мои ошибки», рекомендации ИИ, сертификат-PDF (заглушка), `/arm/help` (методматериалы + таблица горячих клавиш).
- **Проверка:** матрица доступа `02-roles.md` — чужие разделы 403.

### Фаза 6 — Полировка и упаковка (0.5–1 день)
- Демо-путь `06-user-flows.md` (≤5 мин) — прогнан, отрепетирован; скринкаст со звуком (Q&A в12).
- Доступность без смены палитры: фокус-кольца, клавиатура, reduced-motion; замер контраста справочно (перекраска запрещена); RU-даты.
- Ошибки/пустые состояния всех экранов; e2e-smoke демо-пути.
- Сопроводительные артефакты (ТЗ §13/§18): README приложения (сборка/установка/запуск локально, перечень библиотек из package.json), ссылки на спеки.

## 5. Порядок зависимостей (критический путь)

```
Ф0 скелет → Ф1 мок-слой → Ф2 auth+список → Ф3 карточка → Ф4 преподаватель → Ф5 админ+прогресс → Ф6 упаковка
```

Ф4 зависит от Ф3 (мониторинг показывает экран курсанта); Ф5 частично параллелен Ф4 (админка независима — можно вести вторым разработчиком после Ф1).

## 6. Тестовая стратегия

| Уровень | Что | Когда |
|---|---|---|
| Юнит (Vitest) | граф статусов, тайминги нормативов, фильтры поиска, маппинг служб, расчёт баллов/отклонений | Ф1–Ф5 по ходу |
| Компонент (RTL) | форма статуса (обязательность комментария), таймер-бейдж (красный при превышении), таблица списка | Ф2–Ф5 |
| e2e (Playwright) | демо-путь 5 минут: вход преподаватель → занятие → вход курсант → отработка карточки со звонком → отчёт | Ф6 |
| Данные | `validate_mocks.py` в prebuild/CI | всегда |

## 7. Риски и меры

| Риск | Мера |
|---|---|
| Аутентичность «плывёт» при вёрстке | Референс-скриншоты рядом с экраном на ревью; гейт по `07-design-guidelines.md` |
| SSE в локальном контуре | Fallback long-poll; таймеры автономны (клиент от `issuedAt`) |
| 96 карточек ≠ рабочие карточки ПОВ-112 | Рендер карточки — из `fixtures/arm-cards.json`; учебные карточки маппятся на фикстуру по типу (группа ЕКП) — зафиксировать в `shared/api` |
| Объём фаз 3–4 | Каждая фаза сдаётся по критериям приёмки отдельно; недоделанное не блокирует демо-путь (его состав минимален) |

## 8. Критерии завершения проекта

1. Демо-путь проходим без сбоев на чистой машине без интернета (проверка: отключение сети).
2. Все критерии приёмки `04-pages/*` закрыты; гейты раздела 2 зелёные.
3. Матрица `01-requirements-map.md`: все пункты со статусом «С/М» реализованы или честно помечены «этап 2».
4. Скринкаст ≤ 5 минут + README приложения + презентация (отдельный трек, не фронт).
