**Основной путь с 19.10.2026 — Polza.ai, модели Qwen с открытыми весами:** [LIVE-CALLER-POLZA.md](LIVE-CALLER-POLZA.md). SpeechKit (закрытые модели) и Omni (нужен GPU) условию организаторов не соответствуют и остаются прототипами.

**Прежний выбранный режим — SpeechKit + Groq/Qwen:** [настройка, тест и ограничения](LIVE-CALLER-SPEECHKIT.md).
Реальная облачная проверка 19.10.2026 прошла: сгенерированное приветствие без ввода
оператора, распознавание синтетического вопроса про адрес и озвученный ответ.
Ниже сохранена история предыдущих вариантов; GPU-развёртывание не требуется для текущего режима.

## История выбора и предыдущие проверки

**Теперь подключён бесплатный режим Groq + Vosk + Silero:** [запуск и проверенные ограничения](LIVE-CALLER-FREE.md). Реальный API и синтетический PCM-разговор проверены; микрофон человека требует отдельной ручной пробы. Описания неподключённого бесплатного кандидата и GPU-стенда ниже сохранены как история выбора.

**Актуальный путь:** Qwen3-Omni + SGLang-Omni на GPU, непрерывный PCM-вход/выход и прерывание речи. Потоковая интеграция в софтфон добавлена, но настоящий голосовой сервер ещё не подключён. Для запуска выбран один конкретный стенд; [инструкция GPU и настройки backend](../backend/deploy/realtime-qwen/README.md), [контракт](../spec/005-live-caller/realtime.md). Пока нет доступа к GPU, реальный разговор и задержка не проверены.

**После вопроса о бесплатном тесте:** аренда H200 не является обязательным условием realtime вообще. Подготовленный выше GPU-стенд — один вариант. Бесплатный кандидат без аренды: потоковое локальное распознавание Vosk, Qwen3.8-27B через [Groq Free Plan](https://console.groq.com/docs/rate-limits) с потоковым текстовым ответом и локальный синтез Silero. [Веса Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) опубликованы под Apache-2.0. Это отдельный составной голосовой конвейер: Groq не заменяет голосовой realtime endpoint. Такой режим ещё не реализован/подключён, задержка на данном ПК не проверена. Существующий API-клиент старого WAV-прототипа сам по себе эту задачу не решает. Не включать оплату Runpod без отдельного решения пользователя.

Проверки потоковой реализации 19.10.2026: 42 целевых frontend-теста, TypeScript, ESLint затронутых файлов, Steiger и production build прошли. POSIX-синтаксис npm build на Windows потребовал эквивалентного вызова `npx next build` с окружением PowerShell. Backend: 456 passed, 3 failed, 1 skipped; три известных сбоя — два `test_ready_applicant_audio_is_playable_from_recordings` и `test_release_invariants`, они воспроизводились до потоковой реализации. Затронутые realtime/WAV-контрактные проверки проходят (17), Ruff проходит. Настоящий голосовой endpoint в испытании не участвовал.

## Архив WAV-прототипа

**Текущий статус после уточнения пользователя:** описанный ниже обмен WAV-фразами не удовлетворяет требованию realtime. Он отключён в интеграции тренировочного софтфона; вместо проигрывателя показано, что потоковый голосовой сервис ещё не подключён. Ключ такого сервиса или доступ к локальному голосовому серверу пока не настроен. Команды и измерения ниже относятся к предыдущему прототипу, не подтверждают готовность живого realtime-диалога. Для последующего локального развёртывания недостаточно открытых весов одной текстовой LLM: нужно проверить голосовую модель и весь голосовой контур.

После ответа на вызов говорите в гарнитуру: микрофон захватывается один раз и слушает постоянно. Пауза около секунды автоматически отправляет вопрос; начало вашей речи останавливает озвучку заявителя. Есть отключение микрофона и индикатор уровня. Vosk распознаёт законченную фразу, разговорная модель отвечает по билету, Silero озвучивает ответ. LLM может работать через облачный API или локально. STT/LLM/TTS пока обрабатывают фразы целиком, поэтому после паузы остаётся задержка подготовки ответа.

## Сильная модель через API для финала

Уточнение пользователя: сейчас используем облачное размещение модели с доступными весами, перенос на собственные серверы выполняется позднее. Подключение реализовано общим серверным клиентом Chat Completions, без SDK конкретного сервиса и без новых зависимостей. Настройки ниже — пример OpenRouter, не автоматический запуск платных запросов.

Создайте [API-ключ OpenRouter](https://openrouter.ai/settings/keys) и добавьте в `backend/.env` (сохранив JWT_SECRET и настройки вашей БД):

```dotenv
LIVE_CALLS_ENABLED=true
LIVE_CALL_LLM_TRANSPORT=api
LIVE_CALL_LLM_URL=https://openrouter.ai/api/v1
LIVE_CALL_LLM_MODEL=qwen/qwen3-235b-a22b-2507
LIVE_CALL_LLM_API_KEY=вставьте_свой_ключ
LIVE_CALL_REPLY_MODE=auto
```

Затем перезапустите backend. У фронтенда по-прежнему должны быть `BACKEND_URL` и `NEXT_PUBLIC_LIVE_CALLS_ENABLED=true`. Ключ никогда не добавляется во frontend. Без ключа внешний запрос не отправляется; ошибка показана в софтфоне. Сам старт проверяет конфигурацию и локальную речь, не выполняет платную генерацию.

Модель в примере — [Qwen3-235B-A22B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-235B-A22B-Instruct-2507); веса и инструкции развёртывания опубликованы разработчиком. Это кандидат для испытания, качество разговоров через API ещё не замерено. Можно выбрать другую модель в `LIVE_CALL_LLM_MODEL`; проверьте доступность весов и поддержку JSON Schema у выбранного API. У OpenRouter есть [бесплатные модели с лимитами и платные тарифы](https://openrouter.ai/pricing); пример выше не означает бесплатный тариф. Универсальный free-router не фиксирует модель, поэтому для воспроизводимой демонстрации лучше явно выбрать доступную модель с весами.

В режиме `api` значение `auto` включает естественные короткие ответы модели по фактам билета. Адрес и контакты при явном запросе берутся непосредственно из билета. Другие ответы генерируются: промпт запрещает выдумывать события, но это не гарантия; нужны испытания и проверка преподавателем. Для прежнего ограниченного выбора готовых фактов задайте `LIVE_CALL_REPLY_MODE=facts`.

Для последующего локального запуска той же модели используйте совместимый сервер (например, vLLM): смените `LIVE_CALL_LLM_URL` на его base URL с `/v1`, имя модели на локальный alias и ключ на локальный серверный токен. Транспорт `api` означает протокол, а не обязательное внешнее размещение. Для маленькой локальной модели llama.cpp/Ollama ниже есть отдельный вариант; он по умолчанию выбирает готовые факты. Vosk и Silero в обоих режимах остаются локальными.

Проверка API-подключения 19.10.2026: 28 backend-тестов (клиент API, провайдер и контракт звонка), 22 frontend-теста софтфона и полный Ruff прошли. Сетевые ответы API подменены в тестах; проверены Bearer-заголовок, base URL, JSON Schema, сохранение ролей, исключение эталона и ошибки ключа/баланса/лимита. Реальный облачный запрос не выполнялся: ключ ещё не настроен. Результаты локальных измерений ниже относятся к прежнему локальному запуску и не характеризуют облачную модель.

## Подготовка

В `backend/` установите зависимости: `uv sync --extra stt --extra tts`. Модели Vosk и Silero готовятся существующим скриптом `uv run python -m ml.scripts.prepare_models --only stt`, затем `--only tts`. Проверьте допустимые параметры через `--help`, если используете другую версию репозитория.

Для первой пробы используется [Qwen2.5-1.5B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF), файл `qwen2.5-1.5b-instruct-q4_k_m.gguf` (Apache-2.0), в `backend/models/`. Это базовая разговорная модель, не уже имеющийся специализированный semantic-review. Скачать модель и llama.cpp нужно один раз; во время разговора внешний API не нужен.

Из `backend/` запустите имеющийся llama.cpp (PowerShell):

```powershell
.\var\llamacpp\llama-server.exe -m .\models\qwen2.5-1.5b-instruct-q4_k_m.gguf --host 127.0.0.1 --port 8082 --alias caller -c 4096 -ngl 0 -t 4
```

Оставьте его работающим. Для Python backend добавьте в локальный `backend/.env` (сохранив JWT_SECRET, БД и остальные настройки):

```dotenv
LIVE_CALLS_ENABLED=true
LIVE_CALL_LLM_URL=http://127.0.0.1:8082
LIVE_CALL_LLM_MODEL=caller
LIVE_CALL_MAX_SEC=180
```

Для Ollama вместо llama.cpp задайте его URL, установленное имя модели и `LIVE_CALL_LLM_OLLAMA=true`. Не включайте этот флаг для llama.cpp. Адрес и имя модели настраиваются, UI не зависит от провайдера.

В корневой `.env.local` добавьте:

```dotenv
NEXT_PUBLIC_LIVE_CALLS_ENABLED=true
```

`BACKEND_URL` должен указывать на ваш работающий backend. Перезапустите frontend и backend; для production frontend нужна пересборка. На Windows вместо shell-скрипта с Unix-синтаксисом можно запускать `node node_modules/next/dist/bin/next dev`. Backend запускается обычным способом из README, **с одним worker**. Открывайте UI через localhost или HTTPS, иначе браузер не даст микрофон.

## Проверка с гарнитурой

1. Войдите как обучающийся, откройте активное тренировочное задание режима «Специалист-112».
2. Нажмите «Ответить на вызов» и разрешите микрофон. Дождитесь первой фразы; если браузер запретил autoplay, нажмите Play.
3. Скажите «Назовите адрес происшествия» и сделайте паузу около секунды. Вопрос отправится автоматически; повторных нажатий кнопок нет. Проверьте распознанный текст и голосовой ответ. Индикатор уровня должен реагировать на голос. После перезагрузки нажмите «Включить микрофон» один раз.
4. Уточните, что произошло и есть ли пострадавшие; сверьте факты с билетом. Заполните карточку.
5. Завершите разговор; диалог должен сохраниться, индикатор микрофона погаснуть. Проверьте также отказ в разрешении, перезагрузку и недоступный сервер модели.

Короткая модель может ошибаться и терять факты. Прототип не обеспечивает качество диспетчерского тренажёра автоматически: нужны испытания русского диалога и подбор модели на целевом железе. Итоговая оценка остаётся за преподавателем. Чтобы вернуть аудиозаписи, выключите frontend-флаг и перезапустите/пересоберите frontend.

Адрес, имя и телефон при распознанном запросе этих реквизитов озвучиваются непосредственно из билета. Уточнённый эталонный `addressRefined` не передаётся заявителю. Для остальных вопросов LLM выбирает подходящие сведения из словаря, построенного по билету; сервер озвучивает только выбранные факты или короткие стандартные ответы («не знаю», «жду», прощание). Произвольный текст модели не озвучивается. Это ограничивает естественность речи, но исключает добавление моделью выдуманных обстоятельств. Выбор нерелевантного факта всё ещё возможен.

Синтетическая проверка конвейера без микрофона: из `backend/` выполнить `python -m scripts.smoke_live_caller`, затем `python -m scripts.smoke_live_caller --question "Что произошло?"`. Результат и WAV пишутся в `var/live-caller-smoke/`. Используйте Python из backend `.venv` и те же настройки LLM/JWT, что у сервера.
