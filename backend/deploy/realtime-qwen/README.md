# Первый GPU-стенд: Qwen3-Omni

Выбран **Runpod Pod, 1 × H200 141 GB**, NVIDIA CUDA окружение SGLang-Omni. Это отдельная машина, которая предоставляет нашему backend голосовой API. На ПК обучающегося нужны только браузер и гарнитура. После финала тот же сервер и веса можно запустить на собственном GPU. Для первой проверки используем BF16, без дополнительного риска квантования.

**Статус:** конфигурация подготовлена по документации разработчика, GPU не арендован, установка и настоящий разговор на ней не проверены. Код приложения проверяется без модели. Ни качество русского диалога, ни задержку пока не обещаем.

## Стоимость и доступ

На [странице Runpod](https://www.runpod.io/pricing) 19.10.2026 H200 указана по **$5.29/час**; это цена GPU, без отдельного хранения. Итоговая цена и доступность проверяются в консоли перед арендой. Первичная загрузка весов и сборка тоже расходуют время аренды. Нужны аккаунт и баланс Runpod; создание ресурса требует согласованного бюджета. API-ключ Runpod не обязателен для ручного создания Pod. Пароли/ключи не отправлять в чат — доступ к серверу настраивается локально через SSH.

В Pod нужен доступ по SSH, постоянный `/workspace` с достаточным диском под окружение и веса (для первого стенда выбрано 250 GB) и совместимый с CUDA 13 драйвер. В качестве исходного окружения разработчик [рекомендует](https://sgl-project.github.io/sglang-omni/get_started/installation.html) образ `hongccc/sglang-omni:dev`. Тег изменяемый; после выбора образа сохраните его digest в журнале стенда. Внутри ниже фиксируем исходники конкретным commit. Совместимость драйвера и образа должна быть проверена на выделенной машине до дальнейшей настройки.

## Подготовка внутри Linux GPU Pod

Команды выполняются внутри подготовленного CUDA окружения; на Windows их запускать не нужно. Не подключать контейнер к данным пользователя. Загрузка моделей — отдельный подготовительный шаг, в изолированном контуре выполняется заранее.

```bash
git clone https://github.com/sgl-project/sglang-omni.git /workspace/sglang-omni
git -C /workspace/sglang-omni checkout 2d5de98cd92b17df7974ac2ef4192b4a99263845
uv venv --python 3.12 /workspace/omni-venv
uv pip install --python /workspace/omni-venv/bin/python --prerelease=allow -e /workspace/sglang-omni
/workspace/omni-venv/bin/hf download Qwen/Qwen3-Omni-30B-A3B-Instruct --local-dir /workspace/models/Qwen3-Omni-30B-A3B-Instruct
/workspace/omni-venv/bin/hf download pipecat-ai/smart-turn-v3 smart-turn-v3.2-gpu.onnx --local-dir /workspace/models/smart-turn
```

Скопируйте `launch.sh` из этой папки на сервер и выполните `bash launch.sh`. Он проверяет commit и SHA-256 Smart Turn и запускает сервер, доступный только через loopback. Нужен **полный речевой pipeline**: флаг `--text-only` здесь недопустим. Образ/зависимости, полный набор весов и CUDA ещё требуют проверки реальным запуском. Не выключайте Pod до завершения установки, но после теста остановите GPU; хранение может продолжать тарифицироваться.

Выбрана семантическая детекция конца высказывания: она учитывает речь, а не только фиксированную паузу. Модель [Smart Turn](https://huggingface.co/pipecat-ai/smart-turn-v3) имеет BSD-2-Clause; Qwen3-Omni и SGLang-Omni — Apache-2.0. Это потоковый разговор с определением очередности и перебиванием; модель не является постоянно генерирующей full-duplex системой и не обещает нулевую задержку.

## Подключение к нашему backend

На компьютере с backend откройте SSH-туннель, подставив адрес и порт SSH из консоли Pod:

```powershell
ssh -N -L 8008:127.0.0.1:8008 -p <SSH_PORT> root@<SSH_HOST>
```

Добавьте в `backend/.env` (сохраните существующие настройки БД/JWT):

```dotenv
LIVE_CALLS_ENABLED=true
LIVE_CALL_REALTIME_URL=ws://127.0.0.1:8008/v1/realtime
LIVE_CALL_PUBLIC_WS_URL=ws://127.0.0.1:8000/api/v1/operator112/realtime
LIVE_CALL_MAX_SEC=180
```

`LIVE_CALL_REALTIME_KEY` нужен только при подключении к шлюзу с Bearer-аутентификацией; через SSH он не требуется. URL модели недоступен браузеру, ключ провайдера в браузер не передаётся. Не открывайте порт модели в публичный интернет без защиты. В продакшене WS приложения публикуется через `wss` с reverse proxy; установите `LIVE_CALL_PUBLIC_WS_URL` в соответствующий адрес, а HTTP API оставьте на том же origin фронта. POST выдаёт билет, WS принимает его первым сообщением — query-строка не содержит токенов.

У frontend в `.env.local`:

```dotenv
BACKEND_URL=http://127.0.0.1:8000
NEXT_PUBLIC_LIVE_CALLS_ENABLED=true
```

Перезапустите backend **с одним worker** и frontend. При `configured=false` софтфон честно показывает отсутствие сервера; записей и фиктивного разговора нет. `configured=true` означает только наличие настроек, доступность проверяется при соединении. Для теста входите в новую тренировку, нажимайте «Ответить на вызов» и начинайте с обычного приветствия оператора. После обновления страницы — «Подключить голос». Заявитель отвечает на речь; заготовленная первая запись отсутствует.

## Приёмка перед финалом

Проверить по гарнитуре: русский разговор; адрес/контакты из билета; незавершённую фразу с паузой; перебивание в начале и середине ответа; отсутствие поздних звуков отменённого ответа; выключение микрофона; сетевой обрыв; закрытие вкладки; лимит 180 секунд. Зафиксировать фактическую задержку и ошибки ответов. Транскрипт сохраняется в `Attempt.calls` с `kind=realtimeCaller`; отдельного отчёта диалога преподавателю пока нет, звук не записывается. Удалённые инструкции или громкость из динамиков могут влиять на ответы/перебивание — испытание проводится в гарнитуре.

Ограничения интеграции: один backend worker; в нескольких worker потребуются общий store билетов/leases и маршрутизация WS. Отсутствует восстановление истории предыдущего соединения после обрыва: новое соединение начинает новую беседу по тому же билету. Модель может ошибаться в фактах; автоматической гарантии достоверности нет.
