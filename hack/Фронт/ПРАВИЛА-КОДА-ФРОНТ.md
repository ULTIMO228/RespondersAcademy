# ПРАВИЛА НАПИСАНИЯ КОДА ФРОНТА (АРМ-112 / симулятор 112)

Норматив для всех, кто пишет код фронтенда проекта. Основано на методологии
**Feature-Sliced Design** (https://feature-sliced.design) + SOLID + общепринятые практики (KISS, DRY, YAGNI).
Если правило нарушено в коде — код не принимается в ревью. Без исключений «на потом».

---

## Часть 1. Архитектура: Feature-Sliced Design

### 1.1 Слои (только эти, свои слои не придумывать)

```
src/
├── app/        # запуск приложения: роутер, провайдеры, глобальные стили, entrypoint
├── pages/      # страницы (Журнал, Карточка происшествия, Отчёты, Аудит…)
├── widgets/    # крупные самодостаточные блоки (Инцидент-лист, Карточка-виджет, Панель служб)
├── features/   # пользовательские действия с бизнес-ценностью (Форма статуса, Перевод звонка, Добавление службы)
├── entities/   # бизнес-сущности (Incident, Service, Caller, Address, Sms)
└── shared/     # переиспользуемое без бизнеса: UI-kit, api-клиент, lib, config
```

- Слой **processes** — устарел, не использовать.
- **app** и **shared** не имеют слайсов — делятся сразу на сегменты.

### 1.2 Слайсы и сегменты

- **Слайс** — папка внутри слоя, названная по бизнес-домену (`incident-card`, `status-form`).
  Слайс не знает о других слайсах того же слоя.
- **Сегмент** — подпапка слайса по техническому назначению. Стандартные:
  - `ui/` — компоненты, стили, форматтеры отображения;
  - `model/` — типы, схемы, стор, бизнес-логика слайса;
  - `api/` — запросы, типы ответов, мапперы;
  - `lib/` — внутренние helpers только этого слайса;
  - `config/` — флаги, константы слайса.
- Плохие имена сегментов (по сути, а не по назначению): `components`, `hooks`, `types`, `utils`. Запрещены.

### 1.3 Правило импортов (главное правило FSD)

> Модуль может импортировать только из слоёв **строго ниже** своего
> (и из своего же слайса).

| Кто | Может импортировать из |
|-----|------------------------|
| `app` | всех слоёв |
| `pages` | widgets, features, entities, shared |
| `widgets` | features, entities, shared |
| `features` | entities, shared |
| `entities` | shared (и другие entities **только через `@x`**, см. 1.5) |
| `shared` | только shared и npm-пакеты |

Проверяется линтером **Steiger** (`@feature-sliced/steiger`). Ошибки Steiger = ошибка сборки.

### 1.4 Public API каждого слайса

- Каждый слайс экспортируется **только** через `index.ts` (public API).
- В public API выносится **только необходимое**. `export *` — **запрещён**.
- Импортирующий код не должен знать внутреннюю структуру слайса — рефакторинг
  внутри слайса не должен ломать вызовы снаружи.
- Внутри одного слайса — **относительные** импорты с полным путём
  (`../model/useStatusForm`), между слайсами — **абсолютные** через алиас
  (`@/features/status-form`). Импорт из собственного `index.ts` внутри слайса запрещён (кольцевые импорты).

### 1.5 Cross-imports (`@x`-нотация)

Сущности, которые реально связаны (например, `Incident` содержит `Service[]`),
связываются явно: `entities/service/@x/incident.ts` — отдельный public API
только для `entities/incident`. Использовать `@x` только на слое **entities**
и только когда связь объективна (связанные сущности рефакторятся вместе).
Логика взаимодействия сущностей по умолчанию — на слое features/widgets.

### 1.6 Куда что класть (привязка к АРМ-112)

| Код | Слой / слайс |
|-----|--------------|
| Экран «Журнал происшествий» | `pages/journal` |
| Экран «Карточка происшествия» | `pages/incident` |
| Таблица списка происшествий (строки, колонки, фильтры) | `widgets/incident-list` |
| Карточка с таймером, телефонами, адресом | `widgets/incident-card` |
| Панель «Службы» с вкладками и таймлайном | `widgets/service-panel` |
| Форма статуса ДДС (Принята/Начало/Прибытие/Работы) | `features/status-form` |
| Управление звонком (перевод/конференция/сброс) | `features/call-control` |
| «Что случилось?» + опросные карты-теги | `features/incident-type-picker` |
| Блок «Описание со слов заявителя» | `features/statement-form` |
| Тип Incident, его типы/мапперы | `entities/incident` |
| Тип Service, статусы службы, таймлайн | `entities/service` |
| Кнопки, инпуты, модалки, таймер-бейдж | `shared/ui` |
| API-клиент (fetch/axios инстанс, эндпоинты) | `shared/api` |
| Роутер, тема, провайдеры, entrypoint | `app` |

Не reused и ни к чему не относится — остаётся в странице/виджете, слайс не плодим.

## Часть 2. Нормы файлов

### 2.1 Лимиты (мягкие превышения — только после рефакторинга, жёсткие — никогда)

| Что | Лимит |
|-----|-------|
| Файл компонента (tsx) | **≤ 250 строк** |
| Файл логики (hooks, model, lib) | **≤ 150 строк** |
| Файл типов/интерфейсов | ≤ 200 строк |
| `index.ts` (public API) | ≤ 30 строк |
| Функция/хук | **≤ 40 строк** |
| Вложенность (if/for/тернарники) | **≤ 3 уровня** |
| Параметры функции | **≤ 4** (дальше — объект опций) |
| Пропсы компонента | ≤ 7–8 (дальше — композиция или объект-модель) |
| Компонент | 1 компонент = 1 файл, максимум +1 маленький приватный |

### 2.2 Виды файлов и именование

| Вид файла | Имя | Пример |
|-----------|-----|--------|
| Компонент | `PascalCase.tsx` | `StatusForm.tsx` |
| Хук | `camelCase.ts` с префиксом `use` | `useStatusForm.ts` |
| Типы/интерфейсы | `types.ts` в сегменте `model` | `model/types.ts` |
| Стор (zustand/redux) | `store.ts` | `model/store.ts` |
| API-функции | `api.ts` или `api/<name>.ts` | `api/getIncidents.ts` |
| Константы | `constants.ts` | `model/constants.ts` |
| Стили компонента | рядом: `Component.module.scss` | `StatusForm.module.scss` |
| Тест | `Component.test.tsx` рядом с тестируемым | `StatusForm.test.tsx` |
| Public API | `index.ts` | каждый слайс |

- Всё в **kebab-case** на уровне папок: `features/status-form`, `entities/incident`.
- Запрещены файлы `helpers.ts`, `misc.ts`, `common.ts`, `temp.ts`, `new.ts`, `final.ts`, `final2.ts`.

### 2.3 Порядок импортов в файле (группы сверху вниз, пустая строка между группами)

1. Сторонние пакеты (`react`, `zustand`, …);
2. Слои проекта по правилу FSD: `app → pages → widgets → features → entities → shared`
   (внутри — абсолютные алиасы `@/…`);
3. Относительные импорты внутри текущего слайса (`./`, `../`);
4. Стили и ассеты — последними.

Импорты типов — через `import type`. Неиспользуемые импорты — ошибка линтера.

## Часть 3. Именование — чётко и однозначно

### 3.1 Переменные и функции

| Что | Правило | Пример |
|-----|---------|--------|
| Переменная | существительное, содержательное | `incidentList`, `activeService` |
| Функция/метод | **глагол** + объект | `fetchIncidents`, `saveStatus` |
| Обработчик события | `handle<Событие>` / проп `on<Событие>` | `handleSubmit`, `onStatusChange` |
| Булево | `is`, `has`, `can`, `should` + суть | `isTimerExceeded`, `hasVictims` |
| Флаги состояний процесса | `isLoading`, `isError`, `isSaving` | единый словарь, не `loadingFlag` |
| Массив | множественное число | `services`, `linkedCards` |
| Число/количество | `…Count`, `…Total`, `…Index` | `victimCount`, `pageIndex` |
| Константа | `UPPER_SNAKE_CASE` | `TIMER_LIMIT_SECONDS`, `STATUS_LIST` |
| Enum-значения | `UPPER_SNAKE_CASE` или PascalCase, единообразно | `Status.ACCEPTED` |
| Тип/интерфейс | `PascalCase`, без `I`-префиксов | `type Incident`, `interface Service` |
| Generic | `T`, `TData`, `TError` | `<TData>` |
| CSS-класс | BEM через CSS-модули: `block`, `block__elem`, `block__elem--mod` | `.status-form__field--error` |
| CSS-переменная | `--<block>-<property>[-<state>]` | `--timer-color--exceeded` |

### 3.2 Запреты

- `data`, `item`, `info`, `value`, `temp`, `obj`, `arr`, `foo` — запрещены как имена
  (кроме `value` в стандартных колбэках типа `.map((value) => …)`);
- транслит (`statusKarti`, `spisokSlujb`) — запрещён;
- сокращения — только общепринятые: `id`, `url`, `api`, `ui`, `btn` (в тексте кнопок — нет), `ref`;
- однобуквенные переменные — только `i`/`j` в простом цикле и `e` в catch;
- магические числа/строки в коде — **запрещены**, только именованные константы
  (исключение: `0`, `1`, очевидные границы);
- `any` — **запрещён**; `// @ts-ignore` — только с письменным обоснованием над строкой;
- инлайн-стили — только для динамических значений (позиция, ширина из расчёта),
  остальное — CSS-модули с переменными.

### 3.3 Переменные окружения и конфиг

- Только через `shared/config` (re-export из Vite `import.meta.env` / process.env).
- Имя: `VITE_API_URL` и т.п. В коде не обращаться к `process.env`/`import.meta.env` напрямую.

## Часть 4. SOLID на фронтенде

| Принцип | Что значит в React/TS | Пример нарушения |
|---------|----------------------|------------------|
| **S**ingle Responsibility | Компонент/хук/функция — одна причина для изменений. UI-компонент не грузит данные; форма не знает про API | Компонент карточки сам делает `fetch`, хранит стейт и рисует 300 строк JSX |
| **O**pen/Closed | Расширяем через props/композицию, а не правкой компонента | Для нового варианта кнопки меняют её внутренний код вместо `variant` |
| **L**iskov Substitution | Подтипы взаимозаменяемы: пропсы-наследники расширяют, не ломают | Компонент требует `onClick: () => void` вместо `MouseEventHandler` |
| **I**nterface Segregation | Маленькие узкие пропсы/интерфейсы вместо «обо всём» | Один интерфейс `Props { incident, user, services, config, … }` вместо точечных |
| **D**ependency Inversion | Зависим от абстракций: пропсы-колбэки, порты-репозитории, DI через props/context | Компонент импортирует axios и дергает URL напрямую вместо пропа `onSave` / `api` из `shared/api` |

Практические следствия:
- данные получает слой `api`/`model`, а компоненту передаются готовые данные + колбэки;
- побочные эффекты — только в хуках/сторе, не в теле рендера;
- зависимости (localStorage, audio, телефония) — за интерфейсами в `shared/lib`, чтобы в тестах и вне браузера подменять.

## Часть 5. Декомпозиция

### 5.1 Когда дробить компонент

Достаточно **одного** критерия:
1. Файл > 250 строк;
2. JSX с > 3 уровнями вложенности логики / сложными условными блоками;
3. Блок используется в двух местах → вынос в `shared/ui` или `widgets`;
4. В компоненте есть самостоятельная смысловая часть (шапка, форма статуса, панель служб);
5. Внутри > 1 состояния, относящегося к разным частям экрана.

### 5.2 Куда что выносить

- Повторяющийся UI-атом → `shared/ui/<name>`;
- Блок с собственным сценарием → `widgets/<name>`;
- Действие пользователя с бизнес-ценностью → `features/<name>`;
- Логику формы → хук `use<Name>Form` в `model/` или `lib/` слайса;
- Сложные вычисления/мапперы → чистые функции в `lib/` или `model/`;
- Обработчики событий длиннее 3 строк → именованные функции `handle…`, не инлайн-лямбды в JSX.

### 5.3 Хуки

- Один хук — одна ответственность; > 40 строк — дробить на составные хуки;
- хук не должен возвращать «всё подряд»: до 3–4 значений (дальше — объект с понятными ключами);
- хуки только на верхнем уровне компонента/хука, не в условиях и циклах (правило React — без обходов).

## Часть 6. Принципы переиспользования

1. **DRY**: повтор кода > 2 раз — выносить. Но: преждевременная абстракция хуже дубля —
   абстрагируем только по второму-третьему использованию и при понятном контракте (YAGNI).
2. **Переиспользуемое — только из `shared` или через public API нижних слоёв.**
   Никаких `../../../features/other-feature/internals`.
3. Переиспользование — через **композицию** (children, render-props, slots), не через
   копипасту пропсов и не через глубокое наследование классов.
4. Чистые функции (`lib/`) — без скрытых зависимостей; детерминированы, покрыты типами.
5. Универсальный компонент (`shared/ui/Button`) — **без бизнес-логики**. Бизнес-кнопка —
   обёртка в features/widgets, а не условия внутри универсальной.

## Часть 7. Чистота кода (анти-«хаос»)

- **Ранний return / guard clauses**: проверки входа — первыми строками функции, не оборачивать весь код в `if`.
- Вложенность ≤ 3: глубже — выносить функцию или инвертировать условие.
- `switch` со множеством кейсов → таблица соответствий (map-объект) или стратегия.
- Комментарии — **почему**, а не **что**. Устаревший комментарий хуже отсутствующего.
- Закомментированный код — не коммитить (в истории Git он есть).
- `console.log` — не коммитить (только `logger` из `shared/lib` за фичефлагом отладки).
- `TODO/FIXME` — только в формате `TODO(имя): что и к когда`, иначе удаляется.
- Не бросать ошибки «в никуда»: catch либо обрабатывает, либо пробрасывает дальше; пустой catch — запрещён.
- Один формат кода — **Prettier** (настройка в репо, автоформат на сохранении). Споры «табы vs пробелы» — закрыты конфигом.
- ESLint: `@typescript-eslint/recommended`, `react-hooks/rules-of-hooks`, Steiger. Нарушения линтера = нерабочая сборка.

## Часть 8. Состояние и данные

- Локальное состояние UI (раскрыт/закрыт, фокус) — в компоненте (`useState`).
- Состояние сценария (формы, выбранный тип) — в `model/` фичи (zustand/redux по договорённости).
- Глобальное (сессия, пользователь, настройки) — `app/store` или `entities/user`.
- Серверные данные — только через `api`-слой: типы ответа, мапперы в `shared/api`,
  вызовы — в сегменте `api` слайса. Никаких `fetch` в компонентах.
- Нормализация связанных сущностей (Incident ↔ Service) — через `entities/…/@x`, не через дублирование данных.
- Селекторы — мемоизированы; не вычислять тяжёлое в рендере без `useMemo`, где это оправдано профилированием.

## Часть 9. Стили и визуальные константы

- CSS-модули или Tailwind — по договорённости в репо, но **единый подход на весь проект**.
- Все цвета, отступы, шрифты, тени — через CSS-переменные темы (`shared/ui/styles/vars.css`):
  `--color-timer-exceeded`, `--spacing-md`, `--font-ui`. Хардкод hex в компонентах — запрещён.
- Состояния из дизайн-системы АРМ (красный таймер, статусы служб) — именованными переменными,
  чтобы смена дизайна правилась в одном месте.
- Классный тест имени: не глядя на код, по CSS-переменной понятно, где она используется.

## Часть 10. Чек-лист перед сдачей (PR)

- [ ] Код лежит в правильном слое/слайсе; импорты идут только «вниз» (Steiger зелёный)
- [ ] Слайс экспортируется через `index.ts`, без `export *`
- [ ] 1 компонент = 1 файл; лимиты строк не превышены
- [ ] Именование по разделу 3; нет магических значений, `any`, транслита
- [ ] Функции ≤ 40 строк, вложенность ≤ 3, параметров ≤ 4
- [ ] Побочные эффекты только в хуках/сторе; API только через `api`-слой
- [ ] Повторяющееся вынесено; переиспользуемое без бизнес-логики
- [ ] Типы пропсов и сущностей описаны; `import type` где нужно
- [ ] Стили через переменные; инлайн-стили только динамические
- [ ] Линтер и форматтер пройдены без ошибок; `console.log`/закомментированный код удалены
- [ ] В сложном месте — короткий комментарий «почему»
