## 1. Общая суть (пункт 1 листа 1: «Одна платформа: наша и одна для обучения»)

Строится **одна общая платформа** (портал), внутри которой две части
(решение автора концепции, 21.09.2026):

1. **Портал «нашей» платформы** — все модули команды отдельными страницами:
   аналитика, история, советы, справочник, карта, рекомендательная система,
   детекция каскадных ошибок, ИИ-генерация сценариев и контроль генерации
   (состав — [01-ФИЧИ-ПЛАТФОРМЫ](01-ФИЧИ-ПЛАТФОРМЫ.md)).
2. **Учебный симулятор АРМ-112** — визуальная и логическая копия рабочего места
   ГБУ «Система 112»: журнал происшествий, карточка с таймером, опросные
   карты-теги, автоподбор служб, голосовой контур. Требование аутентичности
   интерфейса закреплено заказчиком (единый документ, раздел 6.5; Q&A в.5).
   UI-референсы: `Фронт/Источники/скриншоты_из_docx/`.

**Переход между частями:** на портале — кнопка «Начать учёбу», по ней
обучающийся перекидывается в систему АРМ (симулятор). Обратный переход —
возврат на портал.

Части работают на одних данных (коллекции `users`, `reference`, `cards`,
`scenarios`, `sessions`, `reports` — [МОКИ-ДАННЫЕ](../../Фронт/МОКИ-ДАННЫЕ.md), раздел 1).

## 2. Роли

Три фиксированные роли заказчика (Q&A в.14): **администратор / преподаватель /
обучаемый** (`users.role` — МОКИ-ДАННЫЕ п. 1.1).

У обучаемого — **две подроли** (уточнение автора заметок, важно: это шире,
чем сказано в Q&A):

1. **Оператор 112** (точка A): принимает вызов и заполняет карточку — блок
   «Адрес», данные заявителя, «Описание со слов заявителя», «Добавить тип
   происшествия» и опросную карту, определяет набор вызываемых служб.
2. **Диспетчер ДДС** (точка B): получает заполненную карточку, принимает или
   отклоняет её, проверяет корректность данных (оператор 112 мог ошибиться,
   например, в адресе), дозванивается до руководителей бригад / начальников
   служб (точка C), управляет первичными статусами.

Важное уточнение по Q&A: формулировка «рассматриваем только взаимодействие
B и C» относилась **к телефонии, а не ко всему процессу** (подтверждено
с постановщиком). В голосовом контуре точка A исключена: система поставляет
обучаемому уже сформированную карточку, фокус — звонки диспетчера ДДС (B)
руководителям служб (C) по внутренней IP-телефонии (Q&A в.8).

Матрица функций по ролям — [02-РОЛИ-И-СЦЕНАРИИ](02-РОЛИ-И-СЦЕНАРИИ.md).

## 3. Рамки, заданные заказчиком

Полные формулировки — в едином документе, раздел 6, и в Q&A. Кратко:

| Параметр | Значение | Источник |
|----------|----------|----------|
| Обучаемый | две подроли: оператор 112 (заполнение карточки) и диспетчер ДДС (валидация, статусы, звонки C) | уточнение команды; Q&A в.4 (в части телефонии) |
| Контур | локальный, без интернета; ИИ (STT/LLM/TTS) на CPU | Q&A в.1, в.11 |
| Роли | администратор / преподаватель / обучаемый | Q&A в.14 |
| Нормативы | 30 с — первичная реакция; 3 мин — полная отработка | Q&A в.6 |
| Жизненный цикл | полный: Принята → Начало реагирования → Прибытие → Проведение работ → Работы завершены / Отказ | Q&A в.6; МОКИ-ДАННЫЕ п. 2.1 |
| Голосовой контур | B→C: софтфон, внутренний 3–4-значный номер службы; диалоги **предварительно озвучиваются ИИ**, в систему закидываются готовые записи (TTS в рантайме на CPU не используется) | Q&A в.2, в.8; решение команды |
| Данные | 96 обезличенных билетов = эталоны + датасет генерации | Q&A в.13; МОКИ-ДАННЫЕ п. 3 |
| Формат занятий | офлайн, учебный класс; методика «от простого к сложному» | Q&A в.9 |
| Адаптация | ИИ меняет сложность по скорости и безошибочности (аналогия — подбор соперников в шахматах) | Q&A в.10 |
| Отчёт | ФИО + номер АРМ; метрики по этапам с отклонениями; грамматические ошибки; интегральный балл; графики | Q&A в.16 |
